# Consolidation Audit — Findings & Remediation

Full-codebase audit performed during the consolidation phase. Six parallel
subsystem audits (agent loop + AI client, DB layer, tools, utils/services,
providers, webhooks + core + runtime + config) were cross-checked against the
whole repo, then **every fix was independently re-verified against the real code
path** before and after being applied.

**Baseline before this work:** `tsc` clean, `eslint` clean, 1212/1212 tests
passing, `drizzle-kit check` clean.

That baseline was misleading. The green gates were hiding genuinely broken
features, because in nearly every case the defect was masked by a test double
rather than absent. Examples found and confirmed: the sticker converter's
arguments were mocked away; `test/roomKeyDelivery.test.ts` built fake providers
with no `isOperational` property; `test/DiscordProvider.test.ts` never emitted the
gateway-ready event; the Discord fake had no `error` path. The audit therefore
prioritised *runtime reachability* over static cleanliness.

---

## Verified defects fixed (22)

### 1. WhatsApp was excluded from `activeProviders` on every boot — no delivery lane
**`src/providers/whatsapp.ts:176-224`, `src/runtime/AppRuntime.ts:210-220`** · CRITICAL

`startForGeneration()` sets `providerStatus = 'starting'`, creates the socket and
attaches handlers, then returns. It never awaits `connection === 'open'`, which is
the only place `'running'` is assigned (`whatsapp.ts:256`). So at the moment
`await provider.start()` resolved, `isOperational` was always `false`, and
`AppRuntime` dropped WhatsApp from `activeProviders` — meaning **no WhatsApp
sender** was registered with the webhook server, scheduler or digest service, and
`processOutbox()` built its claim map without `'whatsapp'`, so every WhatsApp
outbox row (reminders, digests, webhook deliveries) was never claimed or sent.
`getReadiness()` read `this.providers`, so `/ready` still returned 200 — green
health over a dead delivery lane.

**Fix:** admission now keys on `start()` resolving, not on `isOperational` at that
instant; a new `operationalProviders()` helper is consulted lazily at delivery
time so a provider that connects late still receives traffic.

### 2. Webhooks returned `202 queued` for deliveries that could never happen
**`src/runtime/AppRuntime.ts`** · CRITICAL

`enqueueWebhook` returned `accepted: true` unconditionally, so the `503` branch in
`WebhookServer.dispatch` was dead code. With no operational provider, clients were
told the event was queued while nothing would ever deliver it. Separately,
`inferWebhookPlatform` fell back to `activeProviders[0]?.name` for unclassifiable
room ids — making the target platform depend on provider start order and
fabricating a room key that then passed `providerRoomTargetMismatch` unchallenged.

**Fix:** the enqueuer returns `accepted: false` (→ 503) when no provider can
deliver, and platform inference refuses to guess rather than fabricating.
Verified end-to-end: declined → 503, accepted → 202.

### 3. `/broadcast` was 100% broken
**`src/tools/ParameterValidator.ts`, `src/tools/OwnerTool.ts`** · CRITICAL

Proven against the real parser: `/broadcast hello world` threw
`Parameter <action> must be one of: broadcast, leave, system_info`. The parser
assigned the first positional token to `action`, and the enum rejected the user's
actual message. The tool's own slash-handling branch was unreachable dead code.

### 4. The owner-only `/role` privilege surface was unreachable
**`src/tools/ParameterValidator.ts`** · HIGH

`role` was missing from `ACTION_ARGUMENTS`, and the generic positional loop read
`effectiveInferred` instead of the resolved action. Proven failures:
`/role setpriv premium contextLimit 50`, `/role resetpriv premium`,
`/role list global`, `/role privs premium` — all threw. These are the documented
owner privilege-override commands.

### 5. `/remind cancel 3` targeted the wrong field
**`src/tools/ParameterValidator.ts`** · HIGH

`number` is the 4th declared property, so the positional loop never reached it and
parsed `{action:'cancel', time:'3'}`.

### 6. Sticker conversion was 100% non-functional
**`src/utils/StickerUtils.ts`, `src/utils/FFmpegConverter.ts`** · CRITICAL

The sticker filter graph failed every allowlist branch (verified empirically:
`VALUE REJECTED: scale='min(320,iw)'…`), and `videoToWebp` also passed
`00:00:00`/`00:00:05`/`default`/`passthrough`, none of which were allowlisted. Both
entry points threw before spawning anything. The pre-existing test mocked the
converter away.

**Fix:** the filter is now defined once in `FFmpegConverter` (single source of
truth for the value that is validated *and* executed) and allowlisted verbatim,
along with its companion values.

### 7. Discord could report a permanently dead client as healthy
**`src/providers/discord.ts:162-184`** · CRITICAL

discord.js 14 never emits `Events.Error` on a non-sharded `Client` — the only emit
site is inside `ShardingManager`'s IPC responder — so that whole error branch was
unreachable. Meanwhile `shardDisconnect`/`shardError`/`shardReconnecting` were
never registered, and `providerStatus = 'running'` was set as soon as `login()`
resolved, which happens when the raw WebSocket connects, *before* gateway READY. A
revoked token or missing `MessageContent` intent therefore produced a dead gateway
that still reported `running` and kept `/ready` at 200.

**Fix:** the dead `error` listener is replaced with the events discord.js actually
emits; `shardDisconnect` is treated as terminal; only `clientReady` may declare the
provider operational.

### 8. `senderPn` was always `undefined` for WhatsApp group messages
**`src/providers/whatsapp.ts:47-51, 366`** · HIGH

The code read `key.participantPn` and `key.senderLid`, neither of which exists on
Baileys' `WAMessageKey` (the real field is `participantAlt`). The fabricated type
extension type-checked but was `undefined` at runtime, so in every group: the
owner could never be matched by phone number, identity upserts lost the PN alias,
and admin matching lost its `senderPn` fallback.

### 9. Unguarded provider calls aborted whole turns
**`src/agent/index.ts:616, 893`** · HIGH

`ctx.react?.('📥')` and `ctx.sendTyping?.()` were the only two of ten such calls
without `.catch(() => {})`. Both providers reject on ordinary API errors, so a
media reaction or a Discord `sendTyping` permission error turned a healthy turn
into "An internal error occurred".

### 10. The turn budget threw out of the tool loop
**`src/agent/index.ts:182, 221-223`** · HIGH

`claimToolCalls` throws `TurnBudgetExceededError` and was the first statement of
`executeRequestedToolCalls`, outside any `try` — so a normal parallel-tool turn
became an internal error and inflated the error metric. Separately,
`constrainTextResult` (which throws once the byte budget is exhausted) was called
from *inside* the loop's `catch`, so a throw there escaped and discarded the whole
turn.

### 11. Unservable reminders hot-looped every 30s forever
**`src/utils/Scheduler.ts:227-237`** · CRITICAL

Both the "no sender" and "target mismatch" paths called `releaseClaim(id, new
Date())`, which sets `remindAt = now` — so the row was instantly due again on the
next tick, forever, logging an error each pass. `retryAttempts` was never deleted
on those paths, so every permanently-failing id was retained for the process
lifetime.

**Fix:** mismatch is terminal (retire on first sight); missing sender backs off
exponentially and retires after `MAX_DELIVERY_ATTEMPTS`; `retryAttempts` is
cleaned on every terminal path.

### 12. Concurrent media downloads deleted each other's temp files
**`src/utils/MediaStorage.ts:244-246`** · CRITICAL

The quota sweep unconditionally unlinked every `.media-*.tmp` except the caller's
own. Up to 4 streams write their temp file concurrently *outside* the IO slot, so
one stream's sweep deleted the others' in-flight files; the writers' fds stayed
valid (POSIX) but their subsequent `rename` failed ENOENT and the download
surfaced as an error.

**Fix:** temp files are only reclaimed after a grace period, well beyond the
slowest legitimate download.

### 13. Cross-room data leak + unindexed lookup in the WhatsApp retry hook
**`src/providers/whatsapp.ts:83-90`** · CRITICAL

`lookupStoredMessage` matched on `provider_message_id` alone. WhatsApp message ids
are unique per chat, not globally, so a colliding id in another room substituted
that room's `raw_message` JSON into the current turn's LLM context. The predicate
was also on the third column of the only available index, forcing a scan of the
largest table.

**Fix:** scoped by `platform` + `chat_room_id` (Baileys already supplies
`key.remoteJid`), which also lets SQLite use the existing
`(platform, chat_room_id, provider_message_id)` index.

### 14. `'retry'` violated the `state` CHECK constraint
**`src/db/runtime.ts:268-276, 453-461`** · CRITICAL (latent)

Both functions bound the caller-facing name `'retry'` directly as the persisted
state. The table only permits `'failed'`/`'dead_letter'`, so every non-dead-lettered
failure threw `CHECK constraint failed` and left the row stuck in
`processing`/`leased`. Masked because both functions have zero production callers
today — a live landmine the moment anyone wires up a drain loop.

### 15. `'unknown'` message ids defeated dedupe and triggered 10 MiB inline embeds
**`src/agent/index.ts:782`, `src/providers/whatsapp.ts:544`** · HIGH

WhatsApp substitutes `'unknown'` when a platform omits an id, and the dedupe index
deliberately excludes placeholders. Matching them made every placeholder history
row look like "current", so each got its media base64-embedded up to
`INLINE_MEDIA_MAX_BYTES` (10 MiB) across the window.

**Fix:** extracted `isUsableProviderMessageId` (`src/agent/messageId.ts`) so the
agent and its tests share one definition of "real id".

### 16. Discord streaming truncated long answers with no error
**`src/providers/discord.ts:450-454`** · HIGH

`editMessage` silently truncated at 2000 chars. The agent streams into a single
live message and sends the final text through the same edit, so any long answer
lost its tail — and because the edit "succeeded", the reply was considered
delivered and never resent. WhatsApp handled the same case correctly by chunking.

### 17. WhatsApp `sendMessage` ignored the AbortSignal
**`src/providers/whatsapp.ts:153-158`** · HIGH

`processOutbox` relies solely on that signal to cancel a slow send. Without it the
underlying call kept running and could still deliver after the outbox had already
failed and rescheduled the row — the recipient got the message twice.

### 18. `MediaRequestTool`'s `try/catch` was unreachable
**`src/tools/MediaRequestTool.ts:133-137`** · HIGH

Three `return this.handle…(…)` calls without `await` meant the `try` block exited
synchronously and a rejection escaped the `catch`, so the user never saw the
"Request failed" message the handler exists to produce. All three sibling tools
already awaited correctly.

### 19. The LLM tool path bypassed mutation limits
**`src/tools/registry.ts`, `src/agent/index.ts`** · HIGH

`runMutatingTool` (mutation cost limit + per-user serialization) was wired only
into the slash-command path, which is not the primary path. The LLM path invoked
tools directly, so neither control applied.

### 20. `additionalProperties: false` was skipped on 2 of 4 tool-loading paths
**`src/agent/index.ts:159, 906`** · MEDIUM

Trigger-matched and `find_tools`-discovered tools were advertised with an open
schema, so the model was told extra keys were fine and then got
`Additional properties are not allowed` on exactly the tools it wanted most.

### 21. `rateWindows` grew without bound
**`src/tools/registry.ts`** · HIGH

One entry per `(tool, user)` pair for the process lifetime; the only clearing
function had zero callers. Expired windows are now swept.

### 22. Further verified fixes
- **i18n `$&` injection** (`src/utils/i18n.ts`) — `replaceAll` with a string
  replacement expands `$&`, so an interpolated value containing `$&` re-injected
  the placeholder (`'a$&b'` → `'a{name}b'`). Values can be user-controlled. Now
  uses a function replacer.
- **`readMediaBuffer` limit mismatch** (`whatsapp.ts`, `discord.ts`) — providers
  downloaded with a 200 MiB cap but read with the 32 MiB default, so anything
  between the two was stored, marked ready, billed against the media budget, and
  then always threw.
- **VP8X dimension precedence** (`src/providers/media.ts`) — `+` binds tighter than
  `|`, so the 24-bit little-endian read was mis-grouped and skewed the pixel
  guards. (The VP8L lines were already correct.)
- **`AuthService` cache staleness** (`src/utils/AuthService.ts`) — a single shared
  `cacheLoadedAt` refreshed by *partial* loads meant an already-cached role was
  never revalidated while any other role loaded more often than the TTL, so
  privilege changes took unbounded time to apply.
- **`MediaCleanup` full scan** (`src/utils/MediaCleanup.ts`) — the common
  no-op-prune path passed `undefined`, selecting every message row with a media
  path and issuing a blocking `existsSync` per row, on a job that runs at startup
  and every few hours.
- **`GroupAdminTool` silent no-op** — returned `''` on permission denial, so the
  agent skipped delivery while still reacting ✅. Now explains itself.
- **Unguarded fixture dumper** (`scripts/dumpFixtures.ts`) — had no
  `NODE_ENV`/`ALLOW_FIXTURE_DUMP` guard at all, so running it in production copied
  real WhatsApp message payloads out of the live database into the repo. Only the
  npm script set the vars; the file was directly invokable.

### Dead code removed
- `src/utils/dbBackup.ts` — an orphaned, *weaker* duplicate of `src/db/backup.ts`
  (no integrity check, no atomic publish, prunes by mtime). Its only consumer was
  its own test, and its header comment falsely claimed `scripts/dbBackup.ts` used
  it. The suite was passing against code that never ran.
- `src/utils/ParameterValidator.ts` — a pure re-export barrel creating a second
  import path. Consumers repointed to the single implementation.
- 7 dead alias exports in `src/tools/registry.ts` (`getAccessibleTools`,
  `canAccessTool`, `getToolDefinitionsForContext`, …) that pointed at functions
  the agent calls by other names.

### Static-analysis gap closed
`tsconfig.json` and the `lint` script excluded `scripts/` entirely — the most
dangerous code in the repo (destructive retention `--apply`, backup restore,
fixture dumping) had zero typecheck and zero lint, and only 3 scripts were checked
at all, transitively via test imports. `scripts` is now in both gates; the two
pre-existing violations were fixed rather than suppressed.

## Recommended follow-up (not yet fixed)

These are verified but were left alone to keep this pass reviewable.

**Correctness / risk**
- `COMMAND_POLICIES` (`registry.ts:99-105`) is an inert security table: every entry
  is unreachable because `isToolInvocationAccessible` prefers `args.__command` over
  `args.action`, so the action never reaches the policy lookup. Not currently
  exploitable (tools re-check internally) but it advertises a control that does
  nothing. Zero test coverage.
- `requiresBinding` (`registry.ts:49, 185`) can never trigger: `hasBinding` is never
  assigned by any caller, so `context.hasBinding === false` is always false. Both
  media tools declare it and it does nothing.
- `message_inbox` is a dedup ledger with no drain loop. `claimInboxEvents` is dead
  code imported only by a test, and `InboxService.admit` hard-codes `payload = '{}'`,
  so stranded rows could not be replayed even if wired up. Four paths strand rows
  (kill mid-turn, queue-full defer, `dropStale`, shutdown drain).
- `closeDatabase` sets an irreversible `defaultClosed` latch when a 5-minute lease
  renewal is missed, so a single long GC/CPU stall permanently bricks the process
  with no re-open path and no log.
- `getMessage` history query (`agent/index.ts:651-663`) ORs five predicates for
  migration tolerance, which defeats both `messages_room_key_created_at_idx` and
  `messages_chat_room_id_created_at_idx` — a full sort of the room's history on
  *every* turn. A `UNION ALL` of index-friendly branches, or a bounded one-time
  backfill so the hot path needs no `OR`, would fix the hottest read in the product.
- No credential reset on WhatsApp `loggedOut` (401) / `badSession` (500): the dead
  session is retried forever and can never re-pair without manual DB surgery.
- `OutboxService` idempotency collides for every `'unknown'`-id message
  (`sha256("whatsapp\0unknown\0assistant")`), so retries can be silently swallowed.
  The inbox already handles the sentinel; the outbox does not.
- `remind in 30 minutes <msg>` still needs a real time/message split. The
  unambiguous `/remind cancel` and `/remind list` are fixed; the bare
  `/remind <text>` form is inherently ambiguous positionally and wants an explicit
  convention (the tool already supports `key=value`).

**Non-unified systems (candidates for consolidation)**
- Five independent `room:<platform>:<id>` builders (`db/rooms.ts`, `agent/roomKey.ts`,
  `messaging/roomKeys.ts`, `AuthService.ts`, `IdentityService.ts`); four validate,
  one does not — and a double-prefixed key silently disables room-scoped roles.
- Three MIME→extension maps; `mimeTypes.ts` claims to be canonical but two of its
  three consumers don't use it, so `audio/mp4` maps to `m4a` in one place and `mp4`
  in another.
- Four independent retry/backoff implementations; `withTimeout` is bypassed by 8+
  call sites; two near-identical token-bucket rate limiters.
- Two divergent `parseRoomKey` implementations: `db/rooms.ts` is strict,
  `agent/roomKey.ts` also accepts `<platform>:<id>`, so the provider-safety guard
  fails open for exactly the input class the agent lane treats as a key.
- `src/db/runtime.ts` is ~400 lines of test-only code that duplicates
  `InboxService`/`OutboxService` with already-divergent semantics (finding 14 is
  one instance of that divergence).
- `scripts/providerStagingHarness.ts` (1013 lines) re-implements the provider
  contract as a fake. Chunking and text limits *are* cross-checked against the real
  exports; the reconnect constants are not, so the lifecycle scenarios validate a
  fake — which is why finding 1 was invisible. Its `start()` reaches `'running'`
  synchronously, unlike the real WhatsApp provider.
- `runStartupCoverageScan` is fully detached: `bootstrap()` constructs
  `AppRuntime` with no deps, so the scan never runs in production.
- `scheduled_deliveries` is a dead table — created, indexed, backfilled,
  retention-scanned, never written or read.

**Platform parity (WhatsApp vs Discord)**
- Missing on Discord: `getGroupInviteLink`, `setGroupSettings`, `leaveGroup`,
  `updateGroupParticipants` for add/promote/demote, owner bootstrap (`seedOwner` —
  so a fresh Discord deployment has zero `owner` users, making `OwnerTool` and
  global role management unreachable), identity upsert, history-sync ingestion.
  `GroupAdminTool` advertises the full action set to the model on both platforms,
  so it offers capabilities that then fail at runtime.
- `BotProvider.lastError` is maintained by both providers and read by nothing, so
  provider failure detail never reaches `/ready`, `/metrics`, or logs.

**Performance**
- `MediaStorage.reconcileMediaQuota` does a full `readdir` plus one `stat` per file
  on *every* media save (~10,000 syscalls at the default cap).
- Unknown-length downloads reserve the entire 200 MiB global budget, so the first
  one blocks the other three download slots (head-of-line).
- `rankMemoriesForInjection` runs a 400-row synchronous blob read plus JS cosine
  similarity on every AI-triggering message.
- Per-message auth resolution is 5-7 sequential SQLite queries before the first
  token is spent, on messages that may not even trigger the AI.
- `WebhookReplayCache.prune()` is O(n) on every webhook request; unauthenticated
  requests are never rate limited (the limiter runs *after* auth), and the
  rate-limit source map is exhaustible by a single noisy client.

**Operational**
- `scripts/` now has static analysis, but the destructive CLIs still have no tests.
- 20 env vars are read by code and documented nowhere, including
  `ENABLE_PLUGIN_RELOAD` — the only kill switch for the owner-only
  `reload_plugins` tool.
- `validateEnv` and `parseWebhookConfig` are divergent validators for the same
  variables; `METRICS_AUTH_TOKEN` passes the startup gate and then aborts
  `AppRuntime.start()` *after* both providers have connected.
- `bootstrap(env)` validates `env` but the webhook server binds from global
  `process.env`, including the security-critical `WEBHOOK_HOST`.
- `webhooks/config.ts` parsers reject empty-string values, so `WEBHOOK_PORT=`
  (exactly how `.env.example` documents it) aborts startup.
- `scripts/dbRoomKeys.ts` prints "room identity is consistent" on an un-migrated
  database (a false green).

## Testing guidance for this codebase

The single most useful lesson from this audit: **the existing test suite's green
status carried almost no information about whether features worked.** The
highest-value change to how this project is tested is to stop mocking the seam
under test when the defect lives in the real code path.

Concrete cases where a mock hid a total feature failure:
- `test/StickerUtils.test.ts` mocked `FFmpegConverter.convert` entirely.
- `test/DiscordProvider.test.ts`'s fake client emitted no lifecycle events and had
  no unreachable-error path.
- `test/roomKeyDelivery.test.ts`'s fake providers omitted `isOperational`, so the
  provider-admission bug could not be observed.
- `test/dbBackup.test.ts` imported the dead duplicate *alongside* the real
  implementation, keeping the orphan alive.
- `test/ProviderStagingHarness.test.ts` cross-checks chunking and text limits
  against the real exports but validates provider *lifecycle* against a fake
  whose `start()` is synchronous — the exact divergence that caused finding 1.

A useful addition to CI would be a reachability assertion per tool: for each
registered tool, assert that a representative invocation reaches the tool's own
`execute` rather than being rejected by validation, admission, or parsing.
