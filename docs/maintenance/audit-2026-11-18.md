## Phase A — Correctness bugs

### A-01 (HIGH) — WhatsApp status broadcasts and newsletter posts are handled as inbound DMs
`src/providers/whatsapp.ts:411-436` (upsert handler), `:471-479` (`createContext`).
The `messages.upsert` handler accepts every `notify` message with a body and `fromMe === false`;
nothing filters `status@broadcast` or `@newsletter`. Baileys decodes both message classes
(`lib/Utils/decode-wa-message.js:157,167`) and upserts them as `notify`
(`lib/Socket/messages-recv.js:1432`, after explicitly handling newsletter stanzas), so every
contact's status update and followed channel post reaches `createContext`. With `isGroup=false`
the agent takes its private-chat path, writes an inbox/message row under
`room:whatsapp:status@broadcast`, spends an LLM turn, and tries to send to the broadcast JID.
**Fix:** drop `status@broadcast` and `@newsletter` jids before context creation (both in the
upsert loop and defensively in `createContext`); test that such a stanza never reaches the
handler.

### A-02 (MED) — `markEnqueuedSent` lacks the duplicate-provider-id guard that `markSent` has
`src/messaging/OutboxService.ts:305-320`; callers `src/agent/index.ts:230-239,1509-1520`.
`markEnqueuedSent` writes `provider_message_id` under
`message_outbox_platform_provider_unique_idx` with no error handling, and both callers sit in a
`try` whose `catch` treats any throw as a *send* failure ("outbox will retry"). CB-13 added the
fallback to `markSent`; the sibling function still has the bug: a colliding provider id turns a
**delivered** reply back into a pending row that is sent again, up to `MAX_ATTEMPTS`.
**Fix:** mirror the `markSent` fallback (retry the update with `provider_message_id = NULL` on a
unique/constraint error).

### A-03 (MED) — A raw room id containing `:` is misparsed as a legacy `<platform>:<id>` key
`src/core/roomKeyFormat.ts:78-91` (`parseRoomReference`);
impact `src/messaging/roomKeys.ts:133-140` and `src/utils/Scheduler.ts:96-111,411-417`.
`parseRoomReference` accepts the pre-migration `<platform>:<id>` form by splitting on the first
`:` for **any** first segment. WhatsApp device JIDs legitimately contain `:`
(`src/utils/jid.ts:10` documents `628123:some:device@s.whatsapp.net`). Verified by execution:
`parseRoomReference('628123456789:12@s.whatsapp.net')` returns
`{platform:'628123456789', remoteRoomId:'12@s.whatsapp.net'}`. A stored reference of that shape
then yields `null` from `remoteRoomIdFromRoomKey`, so the scheduler treats a perfectly good
reminder as "permanent data corruption" and **retires it**, and delivery refuses the room.
**Fix:** only accept the non-`room:` (legacy) branch when its platform segment is a supported
platform; otherwise return `null` so the value is treated as a raw id. Add a `:device@` test.

### A-04 (MED) — Streamed reply bubble is left with a dangling `▌` when the stream fails mid-way
`src/agent/index.ts:1262-1320,1469-1474`.
The `sentKey`/`accumulated`/`streamingFailed` state is block-scoped to the `useStreaming` branch.
If provider iteration throws, the outer `catch` sets an internal-error reply and a second message
is enqueued, but the already-posted bubble still ends in the streaming cursor and is never
finalised.
**Fix:** expose a finaliser from the streaming branch and call it in the iteration `catch`
(and once more on the outer failure path) to strip the cursor; then let the normal fallback
reply follow.

### A-05 (MED) — `MediaConvertTool` appends a second `-vf`, dropping the format's filter chain
`src/tools/MediaConvertTool.ts:58,72-101,213-215`.
`ffmpegArgs = [...FORMAT_ARGS[fmt], ...buildConvertArgs(...)]`. For `gif` the base args already
carry `-vf fps=10,scale=320:-1:flags=lanczos`; a user `resolution`/`fps` adds another `-vf`, and
ffmpeg honours only the **last** one, so `/convert gif resolution=720p` silently loses the palette
fps/scale chain. Verified by reading the merge site.
**Fix:** fold any extra `-vf` into the base `-vf` (base chain first, override last) so exactly one
`-vf` reaches ffmpeg. Add a test asserting one `-vf` with the base chain preserved.

### A-06 (MED) — `AIClient` envelope path buffers a chunked response unbounded
`src/ai/client.ts:300-314`; cf. `src/utils/httpBody.ts`.
The response size guard runs only when `Content-Length` is present; a chunked completion body with
no such header is `response.json()`-buffered whole, defeating `AI_MAX_RESPONSE_BYTES`. This is the
gap `readResponseTextBounded` was introduced to close for SearXNG/scrapes.
**Fix:** read the body through `readResponseTextBounded` and `JSON.parse` the result, preserving
the `response_too_large` / `invalid_response` codes.

### A-07 (MED) — Search results are labelled TRUSTED by a case-sensitive substring match
`src/tools/SearxSearchToolBase.ts:93`.
`this.trustedSites.some(site => itemUrl.includes(site))` labels `https://evil.example/?u=trusted.com`
or `https://nottrusted.com` as trusted, and misses a different-case host. The *filtering* path uses
`site:` scoping; only the label disagrees. Because the label influences the model/user, a
look-alike host reads as vetted.
**Fix:** use the existing `isExactTrustedHostname(itemUrl, trustedSites)` predicate for the label so
it matches `site:` semantics (case-insensitive, host-boundary). Add a look-alike test.

### A-08 (MED) — `FlowHandler` prunes/writes the wrong storage key on the base-key fallback
`src/core/FlowHandler.ts:319-336` vs `clearSessionInternal` `:399-419`.
`getSessionInternal` reads the room-scoped key, then falls back to the room-less base key, but the
prune block always deletes/writes `key` (the room-scoped id), not the key the session came from.
When a legacy base-keyed session has an expired flow this writes a brand-new room-scoped row and
leaves the original orphaned. `clearSessionInternal` already tracks `storageKey`; this path does not.
**Fix:** track `storageKey` and use it for `memorySessions.delete`, `safeDeleteSession`, and
`writeSession`, mirroring the clear path.

### A-09 (LOW) — Tool-progress footer counts every retained line as dropped
`src/agent/toolProgress.ts:189`.
`const dropped = lines.length - 1;` assumes the character cap keeps exactly one line, but
`text.slice(0, end)` usually keeps dozens, so "(+N more steps)" overstates the hidden remainder.
**Fix:** count the lines actually omitted (`lines.length - (kept prefix newlines + 1)`).

## Phase B — Provider robustness

### B-01 (MED) — Discord never retries a failed initial login
`src/providers/discord.ts:281-288`; cf. `whatsapp.ts:253-267,326`, `telegram.ts:375-389`.
On a login failure Discord sets `providerStatus='error'` and throws; unlike the other two providers
it schedules no reconnect. `AppRuntime` calls `start()` once, so a DNS/5xx blip at boot disables
Discord until the process restarts. `reconcileProviderAdmission` (AppRuntime.ts:727) would re-admit
a provider that becomes operational, but nothing re-invokes `start()`.
**Fix:** add the same exponential-backoff `scheduleReconnect(generation)` used by Telegram, invoked
from the login `catch`, cleared on `stop()` and reset on `clientReady`.

### B-02 (MED-LOW) — Telegram stickers are invisible and get no reply
`src/providers/telegram.ts:124-136` (`mediaOf`) vs `:112-122` (`messageTypeOf`).
`messageTypeOf` classifies `sticker` as `stickerMessage`, but `mediaOf` omits it, so `hasMedia` is
false and `mediaAttachments` empty; with empty text the agent drops the message silently. WhatsApp
treats stickers as media.
**Fix:** return the sticker descriptor from `mediaOf`.

### B-03 (LOW) — Telegram quoted/current attachment descriptor never reaches a terminal state
`src/providers/telegram.ts:564-603`.
After `mediaReady` downloads the file it sets only the context-level `mediaPath`/`mimeType`; the
`attachments[0]` descriptor stays `state:'pending'` without `mediaPath`, unlike WhatsApp/Discord
which flip it to `'ready'`. Latent today, but the three providers disagree on one contract.
**Fix:** update the descriptor on success/error in `mediaReady`.

### B-04 (LOW) — Telegram `forwardMessage` does not chunk the forwarded text
`src/providers/telegram.ts:784-792`.
`forwardText` is sent in one `sendMessage`; text over 4096 UTF-16 units is rejected and the whole
forward fails. WhatsApp/Discord chunk first.
**Fix:** chunk with `chunkTelegramText`.

## Phase C — Low-risk cleanups

- **C-01** `Scheduler.deferOrRetire` inlines the backoff formula instead of the shared
  `exponentialBackoff` helper (`Scheduler.ts:577`). Use the helper.
- **C-02** `transcription.ts` has two unreachable branches (`:120`, `:198`); delete them.
- **C-03** `OutboxService`/`InboxService` `fail()` bind the same value to both arms of a
  `CASE WHEN attempt_count >= ?` (`OutboxService.ts:372`, `InboxService.ts:205`). Collapse to a
  single `available_at = ?`.
- **C-04** `InboxService.eventKeyFor` special-cases `''`/`'unknown'` but not `'null'`, while the
  index predicate and `isUsableProviderMessageId` exclude it (`InboxService.ts:55-61`). Route
  through the shared predicate.
- **C-05** `CancellableSemaphore.acquire()` hangs forever when asked for more permits than capacity
  (`semaphore.ts:38-62`). Throw early.
- **C-06** Telegram `updateGroupParticipants` has dead `kick`/`mute`/`unmute` branches
  (`telegram.ts:811-825`) that `GroupAdminTool` never sends. Remove them.
- **C-07** `chunkTextTelegram` doc claims it drops leading newlines; it only `trimEnd`s
  (`textChunking.ts:153-163`). Correct the comment (behaviour is fine) and filter empty chunks.

## Flagged — deferred (need a decision or a contract change)

- **F-01 (upstream, cannot fix here)** `bun audit` high: `picomatch@4.0.7` ReDoS
  GHSA-fc5q-39xc-vjpf, no patched version published. Dev-only transitive. Gate left as is; bump
  the `overrides` pin the moment 4.0.8+ ships.
- **F-02** Telegram quoted attachment download (P-02): `buildQuoted` marks `hasMedia` but
  `downloadToStorage`/`downloadMedia` only read `ctx.msg`, so replying to a photo with
  `/sticker`/`/convert` fails on Telegram while it works on WhatsApp/Discord. Needs a descriptor
  wired through the download path (larger change).
- **F-03** `isPlainObject` accepts `Date`/`Buffer`/`Map`; `stripBlobs` explodes a `Buffer` into an
  index-keyed object. Real only for a live Baileys proto with an uncovered Buffer field. Tightening
  the guard to a prototype check touches many callers; deferred pending a caller audit.
- **F-04** `HealthMetrics` decrements `feedback_total` counters on reaction retraction, which breaks
  Prometheus counter monotonicity. Changing the exposed series is a metrics-contract change.
- **F-05** Reaction-attribution `RecentSendIndex` keys on `platform:messageId` only (not room-scoped),
  so per-chat ids collide across rooms. Telemetry-only; same class as CB-02.
- **F-06** IG-01…09 and PF-01…08 carried over from the 2026-11-17 pass (delivery policy / perf /
  contract items) remain open, each with evidence there.
- **F-07** `BaseHttpClient`'s three bounded readers duplicate `utils/httpBody.ts`'s loop; a refactor
  worth its own commit. `AuthService` DB-override mapping is written twice. `OutboxService`/
  `InboxService` room readers are a copy-paste pair. Duplication only; deferred.
- **F-08** `InboxService.recoverStranded` (`:225-249`) returns expired-lease `processing` rows to
  `received`, but nothing polls `received` and the next scan re-flags them `failed` as "never
  claimed", clobbering any real `last_error`. The recovery branch is a no-op that destroys the
  diagnostic. Fixing it is a delivery-policy change (should `received` rows be re-dispatched?).
- **F-09** `db:backup` refuses a database whose schema fingerprint is stale — the CB-03 crash window
  — so it cannot back up exactly when a backup matters most, even though booting it is fine
  (`backup.ts:155-157`). Needs the same `migrationCount` discriminator boot uses.
- **F-10** Duplicate-event guard in the agent runs after `FlowHandler.handle` and voice
  transcription (`agent/index.ts:672,816` vs the insert at `~836`), so a re-emitted event can advance
  a wizard twice or pay a second transcription when no durable inbox store exists. Reordering is a
  small but real hot-path change.
- **F-11** Streaming send/edit calls have no timeout (`agent/index.ts:1302-1383`), so a provider that
  hangs mid-stream pins a room queue slot indefinitely; only the final reply is bounded.
- **F-12** `ctx.reply` is typed `Promise<void>` and no provider returns an id, so the agent's
  `typeof result === 'string'` provider-id capture (`agent/index.ts:236,1516`) is dead and outbox
  rows for direct sends never carry a provider id. Widen the contract or delete the branch.
- **F-13** `FindToolsTool` ignores `requiresBinding`, so it advertises binding-gated tools to unbound
  users that the agent's `allowedToolNames` then refuses (`FindToolsTool.ts:73-80`). Needs a shared
  `toolVisibleTo` predicate (also duplicated in `MenuTool` and two registry sites).
- **F-14** `WebScrapeTool` declares a `prompt` parameter it never reads (`WebScrapeTool.ts:43`).
  Either wire it into the reader request or remove it; removing a schema property is a tool
  contract change, so it is left for a decision.
- **F-15** `bun audit` is red on `main` for the upstream picomatch advisory (F-01). CI's dependency
  gate will fail until a patched release ships; no code change here can clear it.
