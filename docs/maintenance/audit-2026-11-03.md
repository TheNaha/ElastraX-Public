## 3. Findings & Remediations

### Critical Bugs

#### BUG-001 — Inverted Provider Teardown & SQLite "Database was closed" Crash during Shutdown
- **Severity**: Critical
- **Location**: `src/runtime/AppRuntime.ts:275-279`, `488-510`, `882-894`
- **Root Cause**:
  During graceful shutdown, `AppRuntime.teardown()` closed and drained the `MessageQueue` and processed the outbox *before* stopping the messaging providers (WhatsApp, Discord, Telegram). Incoming messages arriving during queue draining and outbox processing were admitted by providers, queued, and executed. When `runtime.stop()` returned, `src/index.ts` immediately closed SQLite via `database.closeDatabase()`, causing in-flight message handlers to crash with unhandled `"Database was closed"` exceptions. In addition, the outbox flush only processed a single batch of 10 messages, leaving remaining rows un-flushed.
- **Fix Implemented**:
  1. `queuedHandler` now checks `this.stopRequested` and immediately drops incoming messages once shutdown has begun.
  2. Inactive dummy handler `provider.onMessage(async () => {})` is registered on active providers at the start of teardown to stop inbound ingestion.
  3. Replaced single-batch outbox tick with `drainOutbox(timeoutMs)`, looping until all pending messages are delivered or the grace timeout expires.
  4. Outbox draining executes *before* providers disconnect, guaranteeing providers are still operational to deliver outbound messages.
- **Verification**: Verified via `test/AppRuntime.test.ts` (added test `drops incoming messages when stopRequested is set`).

### Integration Gaps

#### GAP-001 — Unsynchronized Flow Processing & Re-entrancy Safety in `FlowHandler`
- **Severity**: High
- **Location**: `src/core/FlowHandler.ts:63`, `199-222`, `438-477`
- **Root Cause**:
  `FlowHandler.handle()` lacked per-session synchronization. Concurrent messages for the same user in an active flow raced during step execution, causing lost state updates or step desynchronization. Simply wrapping `handle()` with `withLock(key)` caused a complete deadlock because active flows invoke `setSession()` or `clearSession()` during step processing or cancellation, which re-acquire the exact same key.
- **Fix Implemented**:
  1. Introduced re-entrant locking in `FlowHandler.withLock` using `AsyncLocalStorage<Set<string>>`. If the current async execution context already holds the session key, acquisition is bypassed.
  2. Wrapped `FlowHandler.handle()` in `this.withLock(key)`.
- **Verification**: Verified via `test/FlowHandler.test.ts` (added test `handle re-entrantly executes flow processors that call setSession or clearSession without deadlock`).

#### GAP-002 — Telegram Context Reply/Send Text Chunking and Cross-Chat Reply Scoping
- **Severity**: High
- **Location**: `src/providers/telegram.ts:534-550`
- **Root Cause**:
  `TelegramProvider.sendMessage` properly split oversized text via `chunkTelegramText`, but `MessageContext.reply()` and `sendMessage()` routed through `sendText` which sent `replyText` in a single un-chunked call. Outputs >4096 characters triggered Telegram API `400 Bad Request: message is too long`, which were caught and swallowed by `bot.on('message')`. Additionally, `reply_parameters: { message_id: msg.message_id }` was passed on chunk 0 even when sending to an external chat via `sendToChat()`, which Telegram rejects.
- **Fix Implemented**:
  1. Updated `sendText` in `src/providers/telegram.ts` to iterate over `chunkTelegramText(replyText)`.
  2. Added chat ID condition: `reply_parameters` is only attached when `i === 0 && targetChatId === String(chatId)`.
  3. Replaced `requireBot('reply')` with `ensureCurrent()` to ensure generation currency.
- **Verification**: Verified via `test/telegram.test.ts` (added tests for multi-chunk replies and `sendToChat` cross-chat sends).

#### GAP-003 — `MakeStickerTool` Dropping `AbortSignal` Leading to FFmpeg Semaphore Starvation
- **Severity**: Medium
- **Location**: `src/tools/MakeStickerTool.ts:61`, `86-96`, `src/utils/StickerUtils.ts:18`, `31-54`
- **Root Cause**:
  `BaseTool.execute` passes `signal?: AbortSignal` to tools. `MakeStickerTool` dropped this parameter, and `StickerUtils.imageToWebp` / `videoToWebp` did not forward abort options to `FFmpegConverter.convert`. On agent timeout (30s), the tool was aborted by the runtime, but FFmpeg subprocesses continued running in the background for up to 120s, exhausting the bounded `PROCESS_SEMAPHORES.ffmpeg` pool (limit = 2) and starving subsequent conversions.
- **Fix Implemented**:
  1. Added optional `options: FFmpegConvertOptions = {}` to `StickerUtils.imageToWebp` and `videoToWebp`.
  2. Accepted `signal?: AbortSignal` in `MakeStickerTool.execute` and passed `{ signal }` to `StickerUtils`.
- **Verification**: Verified via `test/MakeStickerTool.test.ts` and `test/StickerUtils.test.ts`.

### Tech Debt & Duplication

#### TD-001 — Outbox Retry Exponential Backoff Constant Hardcoded to 0
- **Severity**: Medium
- **Location**: `src/messaging/OutboxService.ts:305-327`
- **Root Cause**:
  `OutboxService.fail()` calculated backoff with `exponentialBackoff(0, { baseMs: 5_000 })`, resulting in a flat 5s delay regardless of how many failed attempts occurred.
- **Fix Implemented**:
  Read current `attemptCount` and computed `exponentialBackoff(current.attemptCount, { baseMs: 5_000 })` using the consolidated utility in `src/utils/backoff.ts`.
- **Verification**: Verified via `test/MessagingService.test.ts`.

#### TD-002 — Infinite Reclaiming of Stranded Messages in Outbox and Inbox
- **Severity**: Medium
- **Location**: `src/messaging/OutboxService.ts:178-185`, `src/messaging/InboxService.ts:215-224`
- **Root Cause**:
  Expired leased messages in `OutboxService.claim()` and `InboxService.recoverStranded()` were continuously reset and re-leased even after exceeding `MAX_ATTEMPTS`.
- **Fix Implemented**:
  1. In `OutboxService.claim()`, expired leased rows with `attempt_count >= MAX_ATTEMPTS` are transitioned to `dead_letter` with error `'expired lease: max attempts reached'`.
  2. In `InboxService.recoverStranded()`, rows with `attempt_count >= MAX_ATTEMPTS` transition to `dead_letter` instead of returning to `received`.
- **Verification**: Verified via `test/MessagingService.test.ts` (added unit tests for outbox and inbox dead-letter transitions).

#### TD-003 — Unbounded Tool Execution Error Strings in Agent Loop
- **Severity**: Low
- **Location**: `src/agent/index.ts:37`, `301`
- **Root Cause**:
  When a tool threw an error during execution, `toolResultText` was formatted with `getErrorMessage(err)` without length capping or control-character sanitization, potentially blowing prompt budgets on verbose error strings.
- **Fix Implemented**:
  Bound and sanitized tool error strings with `safeErrorMessage(err, 2000)`.
- **Verification**: Verified via `test/agent.test.ts`.
