## Critical Bugs

### CB-01 — AppRuntime `stop()` drops shutdown requested during boot (FIXED)

**Location:** `src/runtime/AppRuntime.ts` `stop()` (formerly line 457) and `start()` unwind points.

**Evidence:** `stop()` returned early via `if (!this.started) return;` when shutdown arrived while `start()` was mid-boot. Providers already connected during boot were never torn down (sockets, webhook listener, scheduler left ownerless). `start()`'s `stopRequested` checks after provider start were bare `return`s that did not teardown. The code comment at `src/runtime/AppRuntime.ts:220-228` acknowledged this exact failure mode.

**Fix:** Added a persistent `stopped` flag. `stop()` now proceeds to `teardown()` whenever `!started && !stopped` (i.e. during boot, before any completed shutdown), so providers started mid-boot are always released. Once a shutdown has completed, a second `stop()` is a no-op (`stopped === true`). `start()` resets both flags. Teardown was verified idempotent (WebhookServer.stop, Scheduler.stop, MessageQueue.closeAndDrain/beginStop, provider.stop all safe to call multiple times / before start).

**Files changed:** `src/runtime/AppRuntime.ts`

**Verification:** `test/AppRuntime.test.ts` "stop clears timers and shuts down services idempotently" still passes (clearInterval ×7, provider.stop ×1 across double-stop). Full suite green.

## High Bugs

### HB-01 — Agent fire-and-forget media DB backfill (FIXED)

**Location:** `src/agent/index.ts` lines 749-751.

**Evidence:** In the passive-ingestion branch (`shouldTriggerAI === false`), `ctx.mediaReady.then(syncDbMedia).catch(...)` was launched and NOT awaited, so `handleIncomingMessage` returned before the message row's `mediaPath`/`mimeType` was backfilled. A concurrent reader could observe stale/missing media state even though media was on disk. The `shouldTriggerAI === true` branch correctly awaited both.

**Fix:** `await` the background sync so the DB write completes before `handleIncomingMessage` returns. `syncDbMedia` already catches its own errors.

**Files changed:** `src/agent/index.ts`

**Verification:** typecheck, lint, full suite (1557 pass) green.

### HB-02 — WhatsApp `connection.update` async handler unhandled rejection (FIXED)

**Location:** `src/providers/whatsapp.ts` `socket.ev.on('connection.update', async update => ...)`.

**Evidence:** The handler is async but had no top-level error boundary. Operations in the `close`/`open` branches outside the inner `resolveLidForPn` try/catch could throw and become an unhandled promise rejection on the Baileys event emitter.

**Fix:** Wrapped the handler body in `try/catch`, recording `providerError` and logging on failure.

**Files changed:** `src/providers/whatsapp.ts`

**Verification:** WhatsAppProvider test (12 pass) + full suite green.

## Medium Bugs

### MB-01 — WhatsApp `creds.update` synchronous throw escapes handler (FIXED)

**Location:** `src/providers/whatsapp.ts` `socket.ev.on('creds.update', ...)`.

**Evidence:** `Promise.resolve(saveCreds())` evaluates `saveCreds()` eagerly; a synchronous throw from `saveCreds()` propagated out of the event handler before `.catch` was attached, becoming an unhandled rejection.

**Fix:** Changed to `Promise.resolve().then(saveCreds).catch(...)` so a synchronous throw is deferred and caught.

**Files changed:** `src/providers/whatsapp.ts`

### MB-02 — WhatsApp `stop()` `sock.end()` unhandled rejection (FIXED)

**Location:** `src/providers/whatsapp.ts` `stop()`.

**Evidence:** `sock?.end(new Error('Stop called'))` could return a rejected promise that was never caught, surfacing as an unhandled rejection during teardown.

**Fix:** `Promise.resolve(sock?.end(new Error('Stop called'))).catch(...)` with a debug log.

**Files changed:** `src/providers/whatsapp.ts`
