## Phase A — correctness bugs

### A-01 (HIGH) — The webhook replay cache is a hard capacity wall
`src/webhooks/utils.ts` (`WebhookReplayCache.reserve`), response at
`src/webhooks/WebhookServer.ts` (`replay.reservation === 'capacity'`).
`reserve()` refused every new id once `maxEntries` (default **10 000**) reached, and
completed ids live for the whole TTL (**24 h** default BY `WEBHOOK_REPLAY_TTL_MS`); nothing
was evicted while unexpired. A sender emitting >10 000 distinct event ids a day — Jellyfin
playback + CI + Grafana easily — therefore received `503 Retry-After: 1` for the rest of
the window: a permanent intake outage, not a transient one.
**Verified by execution** against the class: with a 24 h TTL and a cap of 100, every id
after the 100th returned `capacity`, and `retry` at t+1 s / t+1 h / t+23 h still did.
**Fix:** evict the oldest completed id at capacity and keep accepting. Insertion order
tracks completion order because `complete()` now delete-then-sets. `capacity` remains only
for the case where every slot is an in-flight request (nothing evictable).

### A-02 (MED) — The replay key omits the sender, so one sender swallows another's event
`src/webhooks/WebhookServer.ts` (`resolveReplayContext`).
The key was `${route}:${id}`, and `route` is `generic` for every sender on `/webhook`. Two
independent senders that number their events (`x-webhook-id: 1, 2, 3…`) collided, and the
second event was answered `202 duplicate` and dropped. The durable layer already keys on
`${route}:${source}:…` (`AppRuntime.enqueueWebhook`) and the rate limiter keys on source;
the in-memory cache was the only layer that disagreed.
**Fix:** key on `${route}:${source}:${id}` (source is resolved before the replay check).

### A-03 (MED) — WhatsApp drops every message queued while the socket was offline
`src/providers/whatsapp.ts` (`messages.upsert`).
The handler required `event.type === 'notify'`. Baileys emits `'append'` for a *new,
never-processed* message when `node.attrs.offline` (`lib/Socket/messages-recv.js:1432`)
and when re-emitting after a decrypt retry (`:346`, `:1257`), so everything sent during a
reconnect vanished with no log, row or reply.
**Fix:** accept `notify` and `append`; app-level dedupe (provider message id / inbox event
key) already protects against a repeat. Test: an `append` upsert reaches the handler.

### A-04 (MED) — A webhook delivery failure left no server-side trace
`src/webhooks/WebhookServer.ts` (`dispatch`).
`allSettled` rejection reasons were discarded and the sanitised `'Delivery failed'` went
only into the HTTP body. A timed-out/aborted send — including the actionable "No sender for
room_id …" diagnostic — was unlogged.
**Fix:** log each rejection with route, room and sanitised reason; HTTP body unchanged.

### A-05 (MED) — Every failed admin action toasted "HTTP 400" instead of its reason
`src/admin/routes.ts` (`api()` in `APP_JS`).
Action failures use the `ActionResult` shape `{ ok, message }`; the browser read only
`body.error`, so `"Row 5 is pending; only failed or dead-lettered rows can be retried."`,
`"No outbox row with id 9."`, `"Reload failed: …"` all became `"HTTP 400"`.
**Fix:** `body.error || body.message || 'HTTP n'`.

### A-06 (MED) — A failed state write after a successful reminder send re-delivered it
`src/utils/Scheduler.ts` (`processReminders`).
The provider send and the `isSent`/`remindAt` update shared one `try`. A `SQLITE_BUSY`
throw on the update hit the delivery-failure path, which re-armed a one-shot reminder
(`claimedAt = null, remindAt = now + backoff`) and sent it again.
**Fix:** bookkeeping has its own `try`; a failure is logged and no longer re-arms delivery.

### A-07 (MED) — The LLM error path buffered the response unbounded
`src/ai/client.ts` (`fetchWithErrorHandling`).
A-06 of the previous pass bounded the success body through `readResponseTextBounded`; the
`!response.ok` branch still used `response.text()` and truncated to 500 chars only after
buffering the whole payload, so `AI_MAX_RESPONSE_BYTES` did not hold where a gateway streams
a large error page.
**Fix:** `readResponseTextBounded(response, 64 KiB, 'LLM error body')`.

### A-08 (MED) — The summarizer accepted only string `content`, unlike the agent
`src/agent/index.ts` (`callLLM` in the summarizer call).
Providers that return an array of text parts, `refusal` or `output_text` yield
`content: null`; the lambda returned `''`, the summarizer threw "empty summary", the
watermark never advanced and **one extra model call ran on every inbound turn** in every
summarizing room.
**Fix:** reuse `extractAssistantText` (the same extractor the reply path uses).

### A-09 (MED) — An oversized tool-call batch made no progress at all
`src/agent/index.ts` (`executeRequestedToolCalls`) with `src/ai/turnBudget.ts`.
`claimToolCalls(count)` rejects the whole batch when it does not fit. With 2 calls left, a
round of 3 executed none, returned "limit exceeded" for all three, and the loop
re-requested the same work until iterations ran out.
**Fix:** grant what fits (`min(ready, remaining)`), run those, and report the limit only for
the remainder.

### A-10 (MED) — After a delivered answer, a later failure sent a contradictory error
`src/agent/index.ts` (`handleMessageInternal`).
The AI-phase `catch` always replied "An internal error occurred", even when a streamed or
direct reply had already been delivered — so the user saw a full answer followed by an
error.
**Fix:** track `deliveredUserVisible` (set by the streamed and direct-send paths) and skip
the error reply when an answer already went out. The durable record is unchanged.

### A-11 (LOW) — The final reply duplicated the durable-send path and lost its guard
`src/agent/index.ts` (final-reply block vs `deliverDurableText`).
Two copies of enqueue/send/mark; the final one had no empty-text guard, so a
whitespace-only `finalAiResponseText` became a blank outbox row and a blank message.
**Fix:** one path (`deliverDurableText`, now returning whether anything was sent).

### A-12 (LOW) — An empty watermark id re-summarized the whole window every turn
`src/ai/summaryStore.ts` (`isWatermark`).
`throughMessageId === ''` passed validation; `entriesAfterWatermark` then found no index and
returned every entry, rewriting the summary on each turn.
**Fix:** require a non-blank `throughMessageId`.

## Phase B — provider consistency

### B-01 (MED) — Telegram GIFs and round videos were not media
`src/providers/telegram.ts` (`messageTypeOf`, `mediaOf`, `MessageCarrier`).
`animation` (a GIF) and `video_note` (a round video) matched no branch, so `hasMedia` was
false and a caption-less GIF/PTV was dropped by the agent — while WhatsApp treats the same
payload as a video.
**Fix:** both map to `videoMessage` and a media descriptor.

### B-02 (MED) — Discord stickers were not media
`src/providers/discord.ts`.
A sticker arrives in `message.stickers`, never `attachments`, so a sticker-only message
(empty content) looked text-less and media-less and was dropped. Telegram and WhatsApp both
surface stickers.
**Fix:** `stickerSources()` synthesises descriptors (PNG/APNG/GIF; Lottie marked
`skipped`), wired into current and quoted sources.

### B-03 (MED) — Telegram mentions matched the bot's numeric id as a substring
`src/providers/telegram.ts` (`isBotMentioned`).
Any group message containing the bot's digits (order numbers, timestamps) started an LLM
turn; the username comparison was case-sensitive while Telegram's is not; a real
`text_mention` of the bot did not count.
**Fix:** count `text_mention` ids, compare `@username` case-insensitively, drop the numeric
substring arm.

### B-04 (MED) — `delete_message` was permanently dead on Telegram, and a group reply to
the bot never triggered the agent
`src/providers/telegram.ts` (`buildQuoted`), `src/tools/DeleteMessageTool.ts`.
The quoted carrier was the raw grammy message, which has no Baileys-shaped `.key`, so
`quoted.rawMessage.key.fromMe` was always `undefined`: `/delete` answered "not a bot
message" and `agent/index.ts`'s "replying to the bot activates the group" check never
fired.
**Fix:** `buildQuoted` synthesises `key: { fromMe, id, message_id, remoteJid }` (Discord
already does this).

### B-05 (LOW) — Telegram streamed at Discord's edit cadence
`src/agent/index.ts`, `src/config/runtime.ts`.
The platform ternary gave Telegram `dcEditIntervalMs` (500 ms), about twice the Bot API's
edit rate; a 429 mid-stream costs a second full-length reply.
**Fix:** `STREAMING_EDIT_INTERVAL_TG` (default 1500) via an explicit per-platform switch.
Documented in `docs/configuration.md` and `.env.example`.

### B-06 (LOW) — Telegram group removal aborted on the first failure
`src/providers/telegram.ts` (`updateGroupParticipants`).
A single `banChatMember` rejection threw out of the loop and left the remaining users
untouched; Discord already used `allSettled` + `AggregateError`.
**Fix:** per-user `allSettled`, aggregate failure like Discord.

### B-07 (LOW) — Telegram "sent" an empty message without sending anything
`src/providers/telegram.ts` (`sendMessage`).
`chunkTextTelegram` returns `[]` for whitespace-only text, so the loop ran zero times and
returned `null`; the outbox then recorded the row as delivered.
**Fix:** throw `UNSUPPORTED` for empty text.

### B-08 (LOW) — WhatsApp native-admin match ignored a device suffix
`src/utils/permissions.ts`.
`matchesParticipant` imported `jidUser`, which keeps `:12` in
`628123:12@s.whatsapp.net`; `jidBareId` (used by `RoleTool` for the same job) strips it, so
the native-admin promotion silently failed for device-addressed participants.
**Fix:** use `jidBareId`.

## Phase C — low-risk cleanups

- **C-01** `validateEnv` did not validate `AI_SUPPORTS_*`, `AI_STREAM_USAGE`,
  `AI_SUPPORTS_PARALLEL_TOOLS` or `AI_MAX_TOKENS_PARAM`; `ModelRouter.envBoolean` throws on
  a bad value on the first chat call, breaking every message instead of startup.
  Added to the startup validation (with tests in `test/config.test.ts`).
- **C-02** `AppRuntime`'s 80-attempt backpressure loop counted each rejection in
  `droppedTasks` and logged 80 warnings for one drop. `MessageQueue.enqueue` now takes
  `{ silent }`; only the final attempt counts and logs (and can still win a freed slot).
- **C-03** `db:backup` reported snapshots as pruned when `unlink` had failed (read-only or
  full volume). `removeFile` returns a boolean; only real removals are counted, failures
  are logged.
- **C-04** `media_search` accepted unvalidated `page`/`media_id` from the slash path; the
  schema now mirrors `media_request` (`integer`, bounds) and `execute` clamps.
- **C-05** The retired-recurring-reminder row was immortal: `retireClaim` left `recurrence`
  set and retention only prunes `is_sent = 1 AND recurrence IS NULL`. `retireClaim` clears
  it.
- **C-06** Dead exports removed: `MessageQueue.isStopped` and `Scheduler.hasTaskRunner`
  (grep over `src`, `test` and `scripts` found only the declarations).

## Flagged — deferred (need a decision, a migration, or a larger change)

- **D-01 (privacy contract)** `/mem revoke` deletes the consent flag but nothing else, and
  the DM prompt builder injects stored memories with no consent check
  (`src/tools/MemoryTool.ts` `revokeConsent`, `src/agent/index.ts` memory block). After a
  revoke, private facts still reach the model provider. Choosing between "gate injection on
  consent", "delete the rows", and "revoke stops only new storage" changes advertised
  behaviour, so it is left for a decision.
- **D-02 (delivery policy)** The durable inbox retries only when a provider redelivers the
  same event: there is no worker that re-dispatches `failed` rows, and the row payload is
  `'{}'` (a dedupe record, not the message), so such a worker cannot exist without
  persisting the event. Backpressure `deferUnclaimed` and aged-out queue tasks therefore
  end as `failed` rows that never run (Telegram/Discord never redeliver).
- **D-03 (retention perf)** `src/db/retention.ts` wraps every timestamp in a `CASE` to
  normalise units, which defeats the index on `flow_sessions(updated_at)`, and `messages`
  has no `created_at` index at all. Fixing it properly is a migration plus
  `REQUIRED_INDEXES` change.
- **D-04 (Telegram laziness)** `TelegramProvider.createContext` downloads the attachment
  eagerly, unlike WhatsApp/Discord (`createLazyPromise`), so a dropped/deduped turn still
  costs a download and a byte-budget slot.
- **D-05 (Discord memory)** `DiscordProvider.forwardMessage` fetches every attachment with
  `Promise.all` into `Buffer`s (up to 10 × 200 MiB) and bypasses the global media budget.
- **D-06 (admin auth behind a proxy)** The admin login throttle keys on the TCP peer, so
  behind a reverse proxy anyone can exhaust the operator's bucket. Needs a
  trusted-proxy/`X-Forwarded-For` policy decision (the webhook limiter already has one).
- **D-07** `MediaBindTool`'s foreign-room "notify" branch requires
  `ctx.verifyRoomMembership`, which no provider supplies, so it is dead for every user.
- **D-08** `OutboxService.enqueueText`'s conflict update resets `attempt_count = 0`, so a
  repeatedly re-enqueued webhook key can never dead-letter. Changing it alters retry
  semantics.
- **D-09** `TTS_BASE_URL` / `EMBEDDING_API_URL` carry a bearer key but are not validated by
  `validateEnv`, so `http://` to a non-loopback host sends the key in clear text. Enforcing
  the https policy could break a self-hosted LAN deployment, so it needs a decision.
- **D-10** `ErrorMetrics`: `recordTokenUsage` keys on the provider-supplied model string, so
  a misbehaving server adds one permanent series per distinct name.
- **D-11** `MenuTool`/`FindToolsTool` re-implement `isToolAccessible` and skip
  `requiresBinding`; `getAuthorizedTool` skips `isToolEnabled`/`requiresBinding`. All are
  currently covered by each tool's own internal check — one new tool that forgets is a
  leak.
- **D-12** Read-mutability tools that declare `cost` (`game_search`, `software_search`) and
  billable read tools (`translate`, `digest`, `transcribe_audio`) are exempt from the
  mutation cost bucket, so they can make paid upstream calls with no per-user throttle.
- **D-13** `scripts/dumpFixtures.ts` duplicates `startupDiagnostics.dumpFixtures`; the
  script (the one wired to `bun run fixtures:dump`) ignores `FIXTURE_DUMP_DIR`, has no row
  cap and writes `0644`, while the hardened copy is test-only. Real WhatsApp payloads can be
  dumped world-readable.
- **D-14** `clearUserIdentities` deletes across platforms and orphans the canonical row
  (test-only today); `MediaService`'s client cache is keyed by secret and never evicts.
- **D-15** Signal handlers are installed after `ensureDatabaseSchema()`/`FlowHandler.initialize()`,
  so a SIGTERM during a long migration skips teardown.
- **D-16** The webhook/admin readiness probe maps a *throwing* check to a bodiless 503,
  losing the diagnostic it exists for; and CSRF verification re-runs the whole session
  check. Both are small but touch the auth path, so they are deferred.
- **D-17** `enqueueText` resetting the attempt counter (see D-08) and `runToolCalls` /
  `beginParallelCall` being production-dead (`AI_MAX_PARALLEL_TOOLS` never enforced; the
  tool loop is sequential) are left as-is: deleting a public method/env var or making the
  loop parallel both change contracts.

## Optional improvements (for you to decide)

- **O-01** `MessageQueue.processNext` still throws synchronously out of `enqueue()` if the

- **O-02** Turn the read-mutability `cost` fields into a startup assertion
  (`cost > 1 ⇒ mutability !== 'read'`) instead of silently discarding them.
