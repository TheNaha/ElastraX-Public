## Critical Bugs

### CB-01 — No Telegram message ever reported media (HIGH)

`src/providers/telegram.ts:818-833` (pre-fix) built its quoted-message carrier with
`{ ...ctx, msg: replyTo }`. grammy exposes `photo`, `video`, `voice`, `document`,
`text` and `caption` as getters on `Context.prototype`; object spread copies only
**own enumerable** properties (`update`, `api`, `me`). Verified by running the real
`grammy` `Context`:

```
ctx.msg: true 5
ctx.photo: undefined
ctx.text: undefined
spread keys: [ "update", "api", "me" ]
```

The same mistake was in the primary path: `mediaOf(ctx as unknown as MessageCarrier)`
at `:519` and `messageTypeOf(ctx)` at `:647`. So `mediaOf` always returned `null`
(`hasMedia` false, `mediaAttachments` empty), `messageType` was always `'unknown'`,
and `downloadToStorage` never found a file. Every Telegram attachment — photo,
video, voice, document, sticker — was invisible to the agent, and no media tool
could reach it.

**Fix:** read the fields from `ctx.msg` / `reply_to_message`, and build the quoted
carrier from the replied-to message. Two new tests drive the handler with a real
grammy `Context` so a plain-object stand-in can no longer hide this class of bug
(`test/telegram.test.ts`).

### CB-02 — The outbox idempotency key was not room-scoped (HIGH)

`src/agent/index.ts:171-173` (pre-fix) keyed an outbox row on
`[messageId, source]`. Provider message ids are only unique *within* a room — a
Telegram `message_id` is a per-chat counter. `OutboxService.enqueueText`
(`src/messaging/OutboxService.ts:110-118`) resolves a conflict with
`ON CONFLICT(platform, idempotency_key) DO UPDATE`, which set `room_key` and
`payload` but **not** `chat_room_id`. Verified by enqueuing two replies with
`message_id=100` in two chats: both returned the same row id, and the row ended up
owned by chat A while its payload was chat B's answer. `deliverOutboxMessage`
then refused it (`providerRoomTargetMismatch`) and `fail()` retired it — so *both*
replies were permanently undelivered.

**Fix:** the room is part of the key, and the conflict clause moves `chat_room_id`
with it. Regression test added (`test/MessagingService.test.ts`).

### CB-03 — A crash between migrate and fingerprint-record bricked startup (HIGH)

`src/db/index.ts:265` (pre-fix) ran `verifyStoredSchemaFingerprint` **before**
`:268` `migrate`, while `:277` `recordSchemaFingerprint` ran after. Any death in
between (OOM, SIGKILL, container stop) left the new schema stored under the old
fingerprint. Because the migrations were already recorded as applied, every later
boot found no pending migration and threw `fingerprint mismatch` forever — manual
SQL was the only recovery. Reproduced against a temp database.

**Fix:** the stored migration count discriminates the two cases. A count *behind*
the journal is exactly the crash window, so the record is re-stamped; a count
*level* with it means the schema changed with no migration, which still refuses.
Also: the runtime-lease guard fired even for callers that explicitly asked for no
lease (`leaseName: null` — tests and `scripts/dbBackup.ts`). Test added.

### CB-04 — `/kb remove <id>` deleted the whole knowledge base (HIGH)

`src/tools/KnowledgeTool.ts:105-111` (pre-fix) had no `ACTION_ARGUMENTS` row, so
the generic parser bound the id to `query` and left `document_id` undefined.
`removeRoomDocument(ctx.roomKey, documentId || undefined)` treats `undefined` as
"delete every chunk". Verified by driving the real parser:
`/kb remove abc123` → `{action:'remove', query:'abc123'}`. Any admin removing one
document wiped the room's corpus.

**Fix:** `knowledge: { index: ['title'], search: ['query'], list: [],
remove: ['document_id'] }`.

### CB-05 — The webhook rate limiter locked out new senders permanently (MED-HIGH)

`src/webhooks/utils.ts:346-351` (pre-fix) pruned only when
`buckets.size >= maxSources`. With the map one below the cap (99/100), prune
returned early forever, so `hasCapacity` was false for any request with two unseen
keys and the request was refused **without storing anything**. Verified by running
`WebhookRateLimiter(10, 60_000, 100)`: fill to 99, then a brand-new pair was
refused, and still refused at +1 s and +10 min, with `size` frozen at 99.

**Fix:** reclaim expired buckets when a request actually needs room, not only once
the map is full. Pruning stays off the hot path (it runs only when capacity is
exceeded).

### CB-06 — One unresolvable subscription row failed every notification (MED-HIGH)

`src/webhooks/WebhookServer.ts:368-376` (pre-fix) called
`resolveSubscriptionDestination` inside `addTarget` with no guard. It throws
`WebhookRequestError(400)` for an unknown platform, a room re-registered on
another platform, or a legacy id — all **permanent** configuration states, and all
derived from the database, not the caller. The throw escaped `handleMediaWebhook`
and returned 400 for *every* subscribed room.

**Fix:** per-target resolution failures are logged and skipped; the original
message is re-raised only when nothing resolved at all, so the single-room case
keeps its existing error contract.

### CB-07 — Telegram reaction updates were never requested (MED-HIGH)

`src/providers/telegram.ts:280` (pre-fix) called `bot.start({ onStart })`. grammy's
`allowed_updates` defaults to `[]`, and Telegram treats `[]` as "all except
`chat_member`, `message_reaction`, `message_reaction_count`"
(`node_modules/grammy/out/bot.d.ts:25-34`). So `bot.on('message_reaction', …)` at
`:435` never fired and the reaction-diff logic added in the previous pass was
unreachable in production.

**Fix:** `allowed_updates: ['message', 'message_reaction']`, with a test that pins it.

### CB-08 — A server that repeats the tool name broke tool calling (MED-HIGH)

`src/ai/streaming.ts:37` (pre-fix) did
`existing.function.name += fragment.function.name` unconditionally. OpenAI-
compatible servers fragment the name (`get_` + `weather`), but some repeat the
*whole* name in every delta; the accumulator then produced
`get_weatherget_weather`, the lookup failed, and tool calling was dead on that
backend. Verified against the accumulator and two new tests.

**Fix:** a repeat that extends the current name replaces it; genuine fragments
still concatenate.

### CB-09 — `every N days` drifted across DST (MEDIUM)

`src/utils/Scheduler.ts:240-246` (pre-fix) computed `amount * 86_400_000` for day
units, while `daily`/`weekly` had already been converted to calendar arithmetic.
A DST change moved `every 1 day` by an hour and the offset persisted, because each
fire re-anchors from the previous `remind_at`. Verified with a pinned
`Europe/Berlin` clock and an injectable `now`; the new test fails against the
pre-fix code.

### CB-10 — A webhook config typo killed the bot after providers connected (MEDIUM)

`parseWebhookConfig` throws on a bad `WEBHOOK_HOST`, `WEBHOOK_CONTAINER_MODE`, any
numeric knob, and even a malformed compat window while the compat path is
disabled. It ran inside `webhookServer.start()`, which `AppRuntime.start()` calls
at `:424` — after every provider started at `:367`. The catch at `:432` tore
everything down and `bootstrap` rethrew. Verified by calling
`parseWebhookConfig` with `WEBHOOK_ENABLED=false` plus a bad host/number/window.

**Fix:** parse the config before any provider starts, when there is nothing to
unwind.

### CB-11 — A short `METRICS_AUTH_TOKEN` aborted startup (MEDIUM)

`src/config/env.ts:201` (pre-fix) passed `METRICS_AUTH_TOKEN` to `validateSecret`,
which rejects any non-empty value under 24 bytes — even though
`readOptionalSharedSecret` (`src/webhooks/config.ts:133-147`) deliberately fails
soft for exactly this token, and `.env.example` documents that a short token
"disables /metrics and the admin dashboard rather than failing the boot".

**Fix:** dropped from the hard-fail list. `WEBHOOK_SECRET` and the per-service
secrets still hard-fail, because intake cannot authenticate without them.

### CB-12 — `OutboxService.prune` deleted rows that `claim()` would still deliver (MEDIUM)

`src/messaging/OutboxService.ts:378-387` (pre-fix) deleted
`state IN ('failed','dead_letter')`, but `claim()` (`:211-220`) takes `failed`
rows with no age predicate. A platform that was not operational for the retention
window (a WhatsApp logout, say) therefore silently discarded every queued reply.
Verified with two `failed` rows that matched `claim`'s exact predicate and were
deleted by `prune(72h)`.

**Fix:** only `dead_letter` rows are terminal and prunable. Long-term
non-terminal rows are reclaimed by `src/db/retention.ts`.

### CB-13 — `markSent` could turn a successful delivery into a retry (MEDIUM)

`src/messaging/OutboxService.ts:322-333` (pre-fix) wrote `provider_message_id`
with no error handling. The partial unique index
`message_outbox_platform_provider_unique_idx` rejects a provider id already
recorded for the same `(platform, chat_room_id)`. The caller
(`AppRuntime.ts:995-999`) catches the throw and calls `fail()`, so a delivered
message was sent again up to `MAX_ATTEMPTS`. Verified by reproducing the
`SQLITE_CONSTRAINT_UNIQUE` throw.

**Fix:** on a constraint violation, record the delivery without the duplicate id.

### CB-14 — No `bot.catch`: any middleware throw stopped Telegram polling (MEDIUM)

grammy's default error handler logs, `await this.stop()`, then **re-throws**
(`node_modules/grammy/out/bot.js:91-101`). The rethrow rejected `bot.start()`,
which the provider turned into `backoff` + reconnect. One handler exception
therefore dropped the message and reconnected the bot.

**Fix:** install `bot.catch(...)` that logs and keeps polling.

### CB-15 — `subscribe`/`bind` read-then-insert raced the unique index (MEDIUM)

`src/utils/NotificationSubscriptionService.ts:186-211` and
`src/utils/ServiceBindingService.ts:36-61` (pre-fix) both did
`select … limit(1)` then `insert` with an `await` in between. The unique indexes
(`notification_subs_user_room_idx`, `service_bindings_user_service_idx`) made the
loser throw `UNIQUE constraint failed` instead of updating.

**Fix:** insert first, treat a unique violation as "someone else created it", then
fall through to the same idempotent update. Shared predicate
`errorUtils.isUniqueConstraintError`.

### CB-16 — The weekly media digest gave up after ~2 minutes (MEDIUM)

`src/utils/DigestService.ts:98, 122-127, 525-535` (pre-fix): `MAX_DIGEST_ATTEMPTS
= 3` and the poll runs every 60 s, so three attempts were spent in about two
minutes. The weekly marker is keyed by the *previous* week, so giving up did not
retry tomorrow — it waited until the next Monday. A short Monday-morning Jellyfin
outage silently dropped the whole week's rollup.

**Fix:** the weekly path gets 30 attempts (each is one Jellyfin call, not a paid
model call).

### CB-17 — `FEEDBACK_LOG_ENABLED=0` also disabled the metrics (MEDIUM)

`src/utils/feedback.ts:162-193` (pre-fix): `recordReactionFeedback` returned early
when `!config.enabled`, skipping `healthMetrics.recordFeedback`. The doc at `:51-52`
says "Metrics are always collected; the eval log is opt-out". Verified.

**Fix:** the counter is always recorded; the flag and the daily ceiling bound only
the JSONL log. Tests updated to the new contract.

### CB-18 — `mergeMax([])` returned `-Infinity` (MEDIUM, latent)

`src/utils/AuthService.ts:96-99`. `getEffectivePrivileges([])` merges an empty
array, producing `-Infinity` for `maxMessagesPerWindow`, `contextLimit` and
`maxDownloadMb`. Not reachable today (every `ctx.resolveRoles()` returns at least
`['user']`), but a negative byte budget is a silent lockout if it ever is.

**Fix:** return `0` for an empty set.

### CB-19 — A reply with `"model": null` was discarded (MEDIUM)

`src/ai/client.ts:330-333` (pre-fix) rejected any non-string `model`, while the
neighbouring `created` field explicitly tolerated `null`. Some gateways send
`"model": null`; the whole answer was then thrown away and the turn ended as
"internal error" after failover.

**Fix:** fall back to the configured model, mirroring `created`.

### CB-20 — `key=value` was unsupported for every tool without a command grammar (MEDIUM)

`src/tools/ParameterValidator.ts:462-500` (pre-fix): only `parseActionSpecific`
extracted `field=value`, and it only ran for tools with a `commandGrammar` or an
`ACTION_ARGUMENTS` row. Verified with the real parser:
`/convert mp3 resolution=720p` → `{format:'mp3', attachment_id:'resolution=720p'}`;
`/sticker attachment_id=foo` → `packname:'attachment_id=foo'`. The token then
reaches a media lookup that throws "Attachment not found".

**Fix:** `knowledge` gained an `ACTION_ARGUMENTS` row. The general hoist is
recorded under DEC-01 (it changes how every grammar-less command parses).

### CB-21 — `groupadmin` required a `user` it then ignored for the quoted flow (MEDIUM)

`src/tools/GroupAdminTool.ts:39-57,136` (pre-fix) marks `user` `required: true`
in every participant variant, so `/kick` as a reply (which `noArgAliases` admits
and `resolveTargetUser` supports via `ctx.quoted.senderId`) failed validation with
`$.user: required for action kick`. The no-argument aliases were dead config that
read like a supported route.

**Fix:** the required flag is dropped for the variants that accept a quoted
target; the tool still returns `group.invalid_phone` when nothing resolves.
(Verified by probing `/kick` against the real parser.)

### CB-22 — An unknown `Content-Length` reserved the whole 200 MiB budget (MEDIUM)

`src/utils/mediaShared.ts:128` returns `maxBytes` when `contentLength` is null, and
`HARD_MEDIA_MAX_BYTES` is 200 MiB. One chunked download (many CDNs omit
`Content-Length`) therefore blocked every other media download until it finished.

**Fix:** the existing delta-growth logic already handles unknown lengths; the
initial reservation is now small and grows with the stream.

### CB-23 — `field=value` plus positionals silently rewrote metadata (MEDIUM)

`src/tools/ParameterValidator.ts:203-224`. `parseActionSpecific` binds overrides
but still feeds leftover positionals into the remaining fields. Verified:
`/pdf edit_metadata title=Report The Final` → `{author:'The', title:'Report',
subject:'Final'}`; `/pdf edit_metadata author=Jane title=My Doc` →
`subject:'Doc'`. No "Unexpected argument" is raised.

**Fix:** recorded under DEC-01; the change alters how free text binds and needs a
decision.

## Integration gaps (flagged)

- **IG-01** `OutboxService.enqueueText` returns the existing id for a `dead_letter`
  or `sent` row without storing the new text, and `AppRuntime.enqueueWebhook` still
  answers `accepted: true`. Re-arming is a policy decision (infinite retries vs
  loss). Unchanged from the previous pass.
- **IG-02** Webhook authentication and the body read happen before the rate
  limiter, so unauthenticated traffic can spend `maxBodyBytes` and HMAC work
  unthrottled. Reordering changes which requests get 429.
- **IG-03** A webhook send timeout returns `502` and releases the replay
  reservation although a provider that ignores the abort can still deliver. Needs
  provider-level idempotency.
- **IG-04** An inbox duplicate that arrives during a retry backoff is accepted by
  `admit()` and then dropped by `claim()` with no log, and no scan ever
  re-dispatches `failed` rows.
- **IG-05** The migration lease is never renewed, so a migration longer than the
  300 s TTL can be run concurrently by a second process.
- **IG-06** A stored room reference containing `:` (a configured
  `!abc:matrix.org` destination) is parsed as a foreign-platform key and every
  delivery is refused.
- **IG-07** A `207` delivery failure body returns server-side subscription room ids
  and a subscriber count to the external media service.
- **IG-08** A webhook destination that cannot be classified (an unregistered id
  with no recognisable shape) is only rejected at dispatch time, so the sender gets
  a retryable `503` for a permanent misconfiguration.
- **IG-09** A signal arriving after the handlers are installed but before
  `runtime` is assigned closes the database while bootstrap continues into
  `runtime.start()`; the `shuttingDown` re-check is a no-op because the shutdown
  promise is already cached.

## Architecture / performance

- **PF-01** `rankMemoriesForInjection` selects its candidate pool by recency
  *before* filtering by embedding space. After an embedding-model change the pool
  can be entirely stale-space, so ranking silently returns `null` and the caller
  falls back to recency. Embedding the query first and filtering in SQL would fix
  it. Flagged (OI-09).
- **PF-02** `HealthMetrics.recordLLMRequest` drops latency for failed requests, so
  p50/p95/p99 exclude timeouts — the slowest requests. Flagged (OI-10).
- **PF-03** `HealthMetrics.recordTokenUsage` keys on the provider-supplied
  `model` string, so a misbehaving server adds one permanent map entry (and one
  Prometheus series) per distinct name. Flagged (OI-11).
- **PF-04** Admin delivery views sort by an unindexed `created_at` (carried over;
  needs a migration).
- **PF-05** `AIClient.chatCompletionEnvelope` bounds the response only through
  `Content-Length`; a chunked response without that header is parsed whole.
- **PF-06** `BaseHttpClient` reports a caller-initiated abort as a retryable
  `NETWORK_ERROR`. No consumer reads `.retryable` today, so this is diagnostic.
- **PF-07** WhatsApp `messaging-history.set` builds a full `MessageContext` (with
  `downloadMedia`, `sendMedia` and closures over the socket) for up to 5000
  messages, then `syncHistoricalDatabase` reads only scalar fields.
- **PF-08** `WhatsAppProvider` downloads the *quoted* attachment for a text-only
  reply that quotes media, pulling up to 200 MiB into the media budget without the
  user asking.
