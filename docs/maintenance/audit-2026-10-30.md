This audit follows the prior Phase 1/2/3 audits and focuses on defects still present

## Critical Bugs

### CB-1 — Lock chain permanently stalls after a rejected task
- **Severity:** Critical
- **Location:** `src/tools/registry.ts:220-236` (`runMutatingTool`), `src/core/FlowHandler.ts:137-149` (`withLock`)
- **Evidence:** both build `queued = previous.then(() => gate)` with no rejection handler. Verified with a promise-chain reproduction: if the held task rejects, `queued` rejects; the next caller awaits `previous` and throws before running or releasing, so the per-user/per-tool (or flow-session) key stays blocked until process restart.
- **Fix applied:** `previous.then(() => gate, () => gate)` in both locations.
- **Verification:** typecheck/lint/tests pass.

### CB-2 — Missing Drizzle snapshot for migration 0024 (CI drift gate)
- **Severity:** Critical (release gate)
- **Location:** `drizzle/migrations/meta/` (no `0024_snapshot.json`), journal entry `0024_drop_scheduled_deliveries` (`when=25`)
- **Evidence:** `bun run db:generate` re-emitted 0024's SQL as a new migration because drizzle-kit diffed against the 0023 snapshot.
- **Fix applied:** added `drizzle/migrations/meta/0024_snapshot.json` (prevId = 0023 snapshot id). Verified `bun run db:generate` now reports "No schema changes".
- **Verification:** `bun run db:check` and `bun run db:generate` clean.

## High Severity

### H-1 — Stale room-key column cache across database handles
- **Severity:** High
- **Location:** `src/messaging/roomKeys.ts:407-429` (`hasRoomKeyColumn`, `resetRoomKeyColumnCache`)
- **Evidence:** cache was a `WeakMap`; reset cleared only the current default handle. `afterMigrationCallbacks` invoked reset with no handle, so a handle migrated via `ensureDatabaseSchema({ database })` could keep a stale `present=false`.
- **Fix applied:** reset now replaces the whole `WeakMap`, invalidating every handle.
- **Verification:** tests pass.

### H-2 — Scheduled task allowlist rejects raw chat ids
- **Severity:** High (usability trap)
- **Location:** `src/utils/scheduledTasks.ts:129-132` (`consumeTaskBudget`)
- **Evidence:** policy stores operator-entered room strings and compares them to canonical `room:<platform>:<id>` keys. Operators commonly enter raw chat ids, so tasks were silently refused even when intended.
- **Fix applied:** match against either the canonical key or its encoded remote room id.
- **Verification:** typecheck/tests pass.

### H-3 — Discord gateway unrecoverable close leaves provider dead
- **Severity:** High (operability)
- **Location:** `src/providers/discord.ts:186-194` (`ShardDisconnect`)
- **Evidence:** on unrecoverable close codes the provider is set to `error` permanently with no reconnect/backoff, unlike WhatsApp/Telegram. Discord.js does not reconnect after these codes by design, so this is partly intentional (bad token/intents).
- **Status:** deferred. Automatic reconnect on auth/intent failures would spin forever; needs a policy decision. Flagged for maintainer.

### H-4 — Duplicate `database_leases` schema definition
- **Severity:** High (maintenance hazard)
- **Location:** `src/db/runtime.ts:42-52` (`ensureLeaseTable`) and `drizzle/migrations/0021_database_safety.sql`
- **Evidence:** the table is created in both places.
- **Status:** not unified. The runtime definition is required as a bootstrap before migrations can acquire the migration lease, so removing it breaks startup/tests. The migration remains the durable definition. Flagged as an accepted, documented duplication.

- **Severity:** Medium

- **Evidence:** retention deletes terminal outbox/inbox rows while AppRuntime also prunes outbox hourly and recovers stranded inbox rows.

### M-4 — Sender abstraction mismatch
- **Severity:** Medium

- **Evidence:** sender signatures differ (`send(roomId, text, platform?)` vs `(chatRoomId, text, signal?)` vs `(platform, chatRoomId, text, signal?)`); `sendMessage` returns `Promise<unknown>` in the interface but `void` in some implementations (assignable, so typecheck passes).

- **Evidence:** senders are registered once at boot from `activeProviders`. They close over the provider object, and webhook enqueue consults `operationalProviders()` dynamically, so late-connecting providers can still receive traffic. No regression observed.
