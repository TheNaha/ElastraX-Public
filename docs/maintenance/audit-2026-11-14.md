## Critical Bugs

### BUG-01 — Discord never leaves `backoff` after a gateway reconnect (HIGH)

`src/providers/discord.ts:183-187` sets `providerStatus = 'backoff'` on
`Events.ShardReconnecting`. The only code that restores `'running'` is `markReady`, bound
to `clientReady`/`ready` (`discord.ts:172-182`), which discord.js emits **once per login**,
not on a resume. There is no `ShardResume`/`ShardReady` handler.

`isOperational` is `status === 'running'` (`discord.ts:83-85`), and
`AppRuntime.operationalProviders()` filters on it (`AppRuntime.ts:427-429`). Therefore a
single transient gateway reconnect permanently removes Discord from outbound delivery:
webhook enqueue reports `accepted:false`, the outbox loses the discord lane, scheduled runs
refuse the platform. Only a process restart recovered it.

**Verified:** read the file and grepped for `Shard`/`resume` (no other handler); confirmed
`Events.ShardResume === 'shardResume'` exists in the pinned discord.js 14.
**Fix:** restore `'running'` on `ShardResume` and `ShardReady`.

A review note flagged that `shardReady` can fire slightly before `clientReady`. Kept anyway:
a reconnect that cannot resume the gateway session emits **only** `shardReady`, so dropping
it would leave those reconnects permanently in `backoff`; and this provider needs the gateway
only for message events and REST sends, both available at shard-ready. The "resumed" log is
emitted only on a real `backoff → running` transition.

### BUG-02 — Final streaming edit failure is reported as a delivered reply (MEDIUM)

`src/agent/index.ts:1212-1218` sends the final edit that removes the `▌` cursor. If that
edit throws, only a warning is logged. `streamedResponseSent` stays `true`, so at
`agent/index.ts:1315` the reply is treated as already delivered:
`OutboxService.recordTextDelivered(...)` is called and no full reply is sent. The user is
left looking at a truncated streamed message still ending in `▌`.

The adjacent `streamingFailed` mechanism (`agent/index.ts:1220-1224`) already exists for
exactly this situation and is documented as "fall through to a regular ctx.reply so the user
still receives the final text". The final-edit path did not use it.

**Verified:** read 1108-1337 and traced both branches that read `streamedResponseSent`.
**Fix:** set `streamingFailed = true` in the final-edit catch so the existing fallback runs.

### BUG-03 — `WhatsAppProvider.stop()` returns before the socket closes (MEDIUM)

`src/providers/whatsapp.ts:182-184` fires `sock.end()` in a floating promise. The 10 s
`Promise.race` in `AppRuntime.teardown` (`AppRuntime.ts:515-527`) therefore always resolves
immediately for WhatsApp, while the websocket, its retry timers and listeners are still
alive after the database has been closed.

**Verified:** read `stop()` and the teardown race. `sock.end()` is `Promise<void>`.
**Fix:** `await` it inside try/catch; the teardown race already bounds it.

### BUG-04 — Telegram `bot.stop()` is fire-and-forget during shutdown (MEDIUM)

`src/providers/telegram.ts:302-308` calls `bot.stop()` without awaiting it. grammy declares
`stop(): Promise<void>` and performs a final confirming `getUpdates`. `index.ts:56` removes
the `unhandledRejection` handler at the start of shutdown, so a rejection here is unhandled
and turns a graceful SIGTERM into a nonzero exit.

**Verified:** read the method; checked grammy's `stop()` signature.
**Fix:** `await bot.stop()` inside the existing try/catch (method is already `async`).

### BUG-05 — Telegram boot-settle timeout orphans a live polling loop (MEDIUM)

`src/providers/telegram.ts:228-235`: the 30 s `settleGuard` rejects the readiness promise but
never stops the bot. `this.bot` still references it, the generation is unchanged and
`desiredRunning` is true, so `isCurrent` keeps passing and the `getUpdates` long-poll
survives. `AppRuntime` has meanwhile dropped the provider from `activeProviders`.

**Verified:** read the guard, `isCurrent`, and AppRuntime's provider admission.
**Fix:** stop the bot and mark the status before rejecting, so no orphaned poller remains.
A follow-up review note was also addressed: the guard now schedules a reconnect exactly like
the sibling polling-failure path, so a slow API at boot does not leave Telegram terminally
dead for the process lifetime. The abandoned bot's close promise is stored and awaited by
`stop()`.

### BUG-06 — A lost inbox lease completes silently (LOW)

`src/runtime/AppRuntime.ts:324` ignores the boolean from `InboxService.complete()`.
If the row's lease was lost, completion fails with no log at all. In a single-process
deployment this is hard to hit (per-room concurrency 1, and the runtime DB lease forbids a
second writer), but the silent path makes the failure invisible if that ever changes.

**Verified:** read `complete()`'s predicate and the call site.
**Fix:** log a warning when it returns `false` (observability only, no behavior change).

### BUG-07 — A brief provider outage permanently destroyed recurring reminders (HIGH)

Two defects combined in `src/utils/Scheduler.ts`:

1. `deferOrRetire()` (used when no sender is registered for the reminder's platform) called
   `releaseClaim(id, nextAttempt)` with no options, so `preserveSchedule` defaulted to false
   and **overwrote `remindAt` with the retry time**. For a recurring reminder that anchor is
   the cadence base, so a single transient error permanently re-based a 09:00 daily reminder
   to whenever the retry happened. The sibling delivery-error path already guards this with
   `preserveSchedule: Boolean(reminder.recurrence)` (`Scheduler.ts:438-450`); the defer path
   did not.
2. The same path retired the reminder after `MAX_DELIVERY_ATTEMPTS = 5`, which with
   30/60/120/240 s backoff is ~8 minutes. A provider that is merely slow to start
   (`AppRuntime` logs "failed to start; continuing in degraded mode") therefore silently
   killed **every recurring reminder for that platform**.

**Verified:** read `deferOrRetire`, `releaseClaim`, the no-sender branch, and AppRuntime's
degraded-mode admission. Covered by two new tests in `test/Scheduler.test.ts`.
**Fix:** pass the reminder, preserve the schedule for recurring rows, and give deferrals their
own counter and a much larger `MAX_DEFER_ATTEMPTS = 24`. Two follow-up review findings were
also fixed: deferrals and send failures no longer share a counter (after an outage had pushed
a shared count past the send cap, the first real send error would retire the reminder), and a
recurring reminder is now never retired by the defer path at all — the next occurrence is its
retry.

### BUG-08 — Reminder claim could be stolen from a still-running task (MEDIUM)

`STALE_CLAIM_MS` was a fixed 2 minutes, but a scheduled agent task may legitimately run for
up to `SCHEDULED_TASKS_TIMEOUT_MS` (max 15 min). A tick that ran while the original task was
still working saw the claim as stale, re-claimed it and ran the reminder a second time —
a duplicate send and a duplicate agent run with tool side effects. This contradicts the
at-most-once semantics documented on `reminders.claimed_at` (`src/db/schema.ts:146`).

**Verified:** read `processReminders`, `taskTimeoutMs`, and the schema comment.
**Fix:** the stale window is now `max(STALE_CLAIM_MS, taskTimeoutMs())`, computed per scan.

### IG-10 — Per-action permission policy is not applied on the LLM tool-call path

`COMMAND_POLICIES` (`src/tools/registry.ts:142-148`) is enforced for slash commands via
`validateAndAuthorizeInvocation` (`registry.ts:328-333`), but the model-driven path calls
the schema-only `validateToolArguments` (`src/agent/index.ts:277`). Tools with per-action
admin requirements (`role.grant`, `config.set`, `language.set`) therefore rely solely on
their own internal checks on the LLM path. Today each such tool does enforce internally, so
this is defence-in-depth rather than a live escalation. **Flagged:** routing the LLM path
through the authorized validator changes the failure message the model sees and could alter
behavior for actions whose internal check is looser than the table. Needs your call.

## Optional Improvements

- **OI-01 (implemented):** cancel the SSE reader on early generator exit
  (`src/ai/client.ts:581-590`) instead of only on `[DONE]`, so an aborted turn cannot leave
  an unread response body holding a keep-alive connection.
- **OI-02 (implemented):** drop a reminder's in-memory retry counter when the reminder row is
  deleted (`src/tools/ReminderTool.ts:340`), so `Scheduler.retryAttempts` cannot retain
  entries for rows that no longer exist.
- **OI-03:** `LoginThrottle` (`src/admin/auth.ts:227`) prunes only expired buckets; a flood
  from many distinct IPs inside one window can exceed the 1000-entry soft cap. Add a hard cap.
- **OI-04:** `DiscordProvider` has no retry for a failed initial login (WhatsApp and Telegram
  both reconnect). A boot-time blip removes Discord for the process lifetime.
- **OI-05:** Remove/un-export the flagged dead exported symbols + `dumpFixtures` (public API
  surface; needs approval).
- **OI-06:** Unify the delivery/mention model (IG-01/02/04) — architecture-level.
- **OI-07:** `RETENTION_DRY_RUN` defaults to `true` (`src/db/maintenance.ts:34`), so a default
  deployment prunes nothing: `messages`, `message_inbox`, `message_outbox` and
  `flow_sessions` grow without bound until an operator opts in. Safer to flag than to flip
  silently — enabling it deletes data on first run.
- **OI-08:** `clearRawMessageBatches` uses a hardcoded 7-day cutoff for nulling
  `raw_message`/`media_path`/`mime_type` (`src/db/retention.ts:152-157`) rather than
  `MEDIA_RETENTION_HOURS`. With a longer media window the DB reference disappears while the
  file remains. Changing it changes how long raw payloads are kept (a privacy/space tradeoff),
  so it is left for your call.
- **OI-09:** `validateSchemaContract` (`src/db/migrations.ts:389`) checks tables, indexes,
  columns and FKs but not the nine room-key/identity triggers, and `recordSchemaFingerprint`
  re-blesses the stored fingerprint in the same startup, so a migration that silently drops a
  trigger is never reported. Adding trigger expectations would strengthen the gate.
- **OI-10:** `drizzle/migrations/0023_*.sql:1` runs `PRAGMA foreign_keys=OFF` inside
  drizzle's migration transaction, where SQLite ignores it (verified empirically). Harmless
  today (nothing references `user_identities` and its triggers are recreated), but the guard
  is illusory for any future table rebuild. The shipped file is immutable, so this is
  documentation only.
