## Critical Bugs

### CB-01: `api/rooms` `createdAt` off by factor of 1000 — RESOLVED (this pass)

**Location:** `src/admin/data.ts:193`

**Evidence:**
```ts
createdAt: room.created_at ? new Date(room.created_at.getTime() * 1000).toISOString() : null,
```
`chatRooms.created_at` is defined as `integer('created_at', { mode: 'timestamp' }).notNull()` (`src/db/schema.ts:41`). With `mode: 'timestamp'` on bun:sqlite, the column reads back as a `Date` whose `.getTime()` is already epoch milliseconds. Multiplying by 1000 produces a date ~1000× too far in the future (year ~53855). The sibling helper `msToIso` (`src/admin/data.ts:221-222`) does `new Date(value).toISOString()` without multiplication, confirming line 193 is the outlier. `ReminderTool.ts:409` correctly passes a `Date` to `reminders.remindAt`, and `admin/data.ts:313` calls `.getTime()` on a `mode:'timestamp'` column, confirming the value is a `Date`.

**Fix:** `createdAt: room.created_at ? room.created_at.toISOString() : null,` — returns the correct ISO-8601 string. Read-side display fix only; no write path, schema, or contract change.

**Why safe:** `room.created_at` is always a `Date` (Drizzle `mode:'timestamp'` + bun:sqlite). Inserts use `new Date()` (`src/db/schema.ts:498`, `src/agent/index.ts:507`). No test pins the old (wrong) value, so no test regression.

## Duplication Found — Safe to Fix

### TD-02: Identical chmod `.catch()` at two sites — RESOLVED (this pass)

**Location:** `src/utils/MediaStorage.ts:72` and `:147`

**Evidence:** Both `saveMediaBuffer` (line 72) and `saveMediaStream` (line 147) end with:
```ts
await mediaStorageDeps.chmod(finalPath, 0o600).catch(error => logger.warn({ err: error }, '[MediaStorage] Failed to restrict media permissions'));
```
(line 147 differs only in parens around `error`). Same file, ~75 lines apart, same logic, same message, same purpose (best-effort permission restriction after rename).

**Fix:** Extract to a module-level helper `restrictMediaPermissions(finalPath)` and call it at both sites.

### TD-03: Identical `processReminders()` `.catch()` at two sites — RESOLVED (this pass)

**Location:** `src/utils/Scheduler.ts:292` and `:294`

**Evidence:** `Scheduler.start()` (line 292) and its `setInterval` callback (line 294) both contain:
```ts
void this.processReminders().catch(error => logger.error({ err: error }, 'Reminder processing failed'));
```
Same function, 3 lines apart, identical error message.

**Fix:** Deduplicate into a single call site (invoke `processReminders()` once at start, then let the interval re-invoke it; or extract a local `scheduleReminderProcessing()` helper). Chose: keep the immediate invocation, extract the catch into a tiny local helper so both sites share one logging shape.

### TD-04: `instanceof Error` coercion not routed through `errorUtils.toError()` — RESOLVED (this pass)

**Location:** `src/utils/mediaShared.ts:117`

**Evidence:**
```ts
export function throwIfAborted(signal?: AbortSignal): void {
  if (signal?.aborted) throw signal.reason instanceof Error ? signal.reason : new Error('Media download aborted.');
}
```
This is exactly the `toError()` idiom that `src/utils/errorUtils.ts:35` exists to centralize. All other sites were unified onto `safeErrorMessage`/`toError` in prior passes (audit-2026-11-08 Phases 1-2); this one was missed because it lives in `mediaShared.ts` rather than a provider.

**Fix:** `throw toError(signal.reason ?? new Error('Media download aborted.'));` plus import `toError`.

**Behavior note (intentional minor widening):** `toError(signal.reason ?? new Error('Media download aborted.'))` is behavior-identical to the inline coercion for all realistic `AbortSignal.reason` values (`Error` or `undefined`). It differs only for a non-Error, non-nullish reason (e.g. a string): the old code discarded it and threw `new Error('Media download aborted.')`, while `toError` preserves the string as the message. This is arguably more correct, and `throwIfAborted` is exported, so any caller matching on `.message === 'Media download aborted.'` for string reasons would see a different message. No test or caller in the repo does this. Documented here for transparency.
