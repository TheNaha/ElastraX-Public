## Critical Bugs

### BUG-01 — A boot-time provider failure permanently removes that platform from every durable delivery lane (HIGH)

`src/providers/whatsapp.ts:296-299` and `src/providers/telegram.ts:246-266` both schedule a
reconnect and then **reject** `start()`. `AppRuntime.start()` (`src/runtime/AppRuntime.ts:370-383`)
admits a provider only when `start()` fulfils, and `operationalProviders()`
(`AppRuntime.ts:432-434`) — which gates webhook enqueue, the outbox claim, and scheduled runs —
iterates that boot-time snapshot forever. The provider's own retry loop later connects and flips
`status` to `running`, but nothing is listening: the platform never gets a sender registered and
`operationalProviders()` never includes it again. One blip during boot removes a platform until
the process restarts.

**Verified:** read both `start()` implementations, the reconnect path, `operationalProviders()`
and every caller; `activeProviders` is assigned once at `AppRuntime.ts:370` and never appended.
**Fix:** re-admit providers that became operational after boot, and widen
`operationalProviders()` to the full provider list. AppRuntime already attaches inbound handlers
for every provider (`AppRuntime.ts:348-350`), so only the outbound lanes were missing.

### BUG-02 — Any group member can wipe a room's knowledge base (HIGH)

`src/tools/KnowledgeTool.ts:33` declares `permissions = 'user'`, `groupOnly = true`, and the
file never calls `ctx.checkPermissions`. `action: 'remove'` with no `document_id`
(`KnowledgeTool.ts:78-101`) clears the whole room corpus; `action: 'index'` overwrites it. The
sibling room-scoped writer, `MemoryTool` (`src/tools/MemoryTool.ts:177`), requires `admin` for the
same kind of write, so the two disagree about who may destroy room data.

**Verified:** read the tool; grepped for `checkPermissions` (only `MemoryTool` has it).
**Fix:** require `admin` for the mutating actions (`index`, `remove`), reusing the existing
`memory.no_group_permission` key.

### BUG-03 — `/admin` parses request bodies with no size limit (HIGH)

`src/admin/routes.ts:175` (unauthenticated `api/login`) and `src/admin/routes.ts:253`
(`handleAction`) call `await req.json()` directly. The webhook path is bounded
(`src/webhooks/WebhookServer.ts:496`, `readRequestBytesWithLimit`), and the `Bun.serve` instance
sets no `maxRequestBodySize` (`WebhookServer.ts:610`), so a client can push a very large body
into a full JSON parse on the event loop before any authentication happens.

**Verified:** read both call sites and the server construction; `Bun.serve` options contain only
`hostname`, `port`, `error`, `fetch`.
**Fix:** read admin bodies through the existing capped reader with a small limit.

### BUG-04 — Discord ignores the delivery abort signal on the reply path (MEDIUM)

`src/providers/discord.ts:506-517` (`reply`) never consults `options.signal`, and
`sendToChat` (`:541-545`) checks it once and then forwards no signal, so `sendToProvider`
(`:420`) reaches `sendMessage` without one. WhatsApp (`src/providers/whatsapp.ts:220-230`) and
Telegram (`src/providers/telegram.ts:360-368`) both check the signal between chunks. The
agent's final answer is delivered under a cancellable timeout
(`src/agent/index.ts:1334`), so a timed-out send can still deliver after the caller has
recorded a failure and rescheduled — the exact double-delivery hazard documented in WhatsApp.

**Verified:** read all three provider send paths and `deliverDurableText`.
**Fix:** check the signal before each chunk and thread `options.signal` through `sendToChat`.

### BUG-05 — A failure before the AI phase leaves the user with no reply (MEDIUM)

`handleIncomingMessage` (`src/agent/index.ts:462`) opens its `try` only at `:687`; the room
lookup/insert (`:473-511`), `AuthService.getAccessProfile` (`:517`), `FlowHandler.handle`
(`:569`) and `getAuthorizedTool` (`:582`) can all throw outside it. The rejection reaches the
provider's handler, which only logs, so the user is silently ignored and the
`agent.internal_error` path at `:1368-1372` is never used.

**Verified:** read the function's structure and the provider `onMessage` error handlers.
**Fix:** wrap the exported entry point in a catch that logs and sends the same localized
internal-error message the AI phase uses. The existing inner catch already returns normally, so
the wrapper never double-replies.

### BUG-06 — Chain-of-thought is rendered to the user while streaming (MEDIUM)

`src/agent/index.ts:1141` accumulates `delta.content` and renders it verbatim with the cursor
(`:1145`), while the final edit (`:1209`) and `extractAssistantText` (`:394`) run
`stripThinkTags`. A reasoning model's `…` block is therefore shown in chat for the whole turn
and then disappears.

**Verified:** read the streaming loop, the final edit and `stripThinkTags`
(`src/utils/textUtils.ts:14`).
**Fix:** display `stripThinkTags(accumulated)`.

### BUG-07 — Group memories are deduplicated against knowledge-document chunks (MEDIUM)

`findSemanticDuplicate` (`src/utils/semanticMemory.ts:121-135`) and
`rankMemoriesForInjection` (`:167-178`) filter only on `ownerId`. For group scope that id is the
canonical room key (`src/tools/MemoryTool.ts:37-39`) — the same owner used for
`category='document'` chunks written by `src/utils/roomKnowledge.ts:205`. A group memory that
resembles an indexed document is rejected as `memory.duplicate` (showing the document text), and
document chunks consume the 400-row candidate pool.

**Verified:** read both queries, the room-knowledge writer and the MemoryTool caller.
**Fix:** exclude the document category from both memory queries.

### BUG-08 — Boundary-aware chunking only breaks in the last quarter of the limit (MEDIUM)

`lastBreakBefore` (`src/utils/textChunking.ts:23-29`) is given the window
`characters.slice(searchStart, end)` and then applies `floor = limit / 2` to *that slice*, so a
break is only accepted in the last 25 % of the limit. A ~1200-character Discord message is
therefore hard-split at 2000 instead of breaking at a paragraph. `end = searchStart + breakAt + 1`
also advances by one past the delimiter, leaving the second `\n` of `\n\n` at the head of the
next chunk.

**Verified:** read the helper and its two call sites; traced a 1500-char input with a `\n\n` at
offset 900 by hand.
**Fix:** search the window from its own start and advance past the whole delimiter.

### BUG-09 — `/reload` cannot pick up edited plugin code and leaks its reports (MEDIUM)

`src/tools/registry.ts:525` does `await import(filePath)` with no cache-busting specifier, so
Bun's module cache returns the previously evaluated module — the tool only ever sees newly
*added* files, contradicting `src/plugins/ReloadPluginsTool.ts`'s description. Separately,
`pluginReports` (`registry.ts:496-500`) is module-level and never reset, so every reload appends
another full set (`:531,554,565`).

**Verified:** read the loader, the report array and the tool's manifest text.
**Fix:** import with a generation suffix and reset the report list per load.

### BUG-10 — `MakeStickerTool` reports success when it cannot deliver (MEDIUM)

`src/tools/MakeStickerTool.ts:103-109`: when the platform has no `sendSticker`, the tool replies
"not supported" and then returns `sticker.success`, so the model is told the sticker was sent
when it never was.

**Verified:** read the branch and its return value.
**Fix:** return the localized "not supported" text instead of the success string.

### BUG-11 — `PDFTool` escapes its error handling for two actions (MEDIUM)

`src/tools/PDFTool.ts:143-144` dispatches `img_to_pdf`/`merge_pdfs` *before* the guarded block
that starts at `:150`, so a `resolveTargetMedia`/`FlowHandler.setSession` failure throws out of
`execute` instead of returning a localized error. `:213` also returns `pdf.invalid_pages` for an
invalid `degrees` value.

**Verified:** read the dispatch and both branches.
**Fix:** move both calls inside the guarded block; add a `pdf.invalid_degrees` key.

### BUG-12 — WhatsApp reconnect leaves a floating socket-close promise (MEDIUM)

`src/providers/whatsapp.ts:266` calls `existingSocket.end(new Error('Restarting WhatsApp socket'))`
without awaiting or catching it — unlike `stop()` (`:186`). A rejection is an unhandled promise
rejection, which is fatal during shutdown after `src/index.ts:56` removes the handler.

**Verified:** read both call sites.
**Fix:** await it inside the existing try/catch.

### BUG-13 — Discord `forwardMessage` buffers arbitrary attachments without limits (MEDIUM)

`src/providers/discord.ts:491-495` fetches each attachment with no `response.ok` check, no
`validateDiscordMediaUrl` (used by `downloadDescriptor` at `:351`), and
`Buffer.from(await response.arrayBuffer())` of unbounded size, unlike the streaming
`saveMediaResponse` path with `HARD_MEDIA_MAX_BYTES`.

**Verified:** read the branch and the guarded path beside it.
**Fix:** validate the URL, require `response.ok`, and cap the copied bytes.

### BUG-14 — The auth privilege cache TTL is reset by single-role loads (MEDIUM)

`src/utils/AuthService.ts:564` stamps the shared `cacheLoadedAt` while loading one role's
overrides, so a frequently-read role keeps every other role's cached privileges alive past
`CACHE_TTL_MS` — the same class of bug the comment at `:428-431` says was fixed for
`getEffectivePrivileges`.

**Verified:** read `getDbOverrides`, `cacheLoadedAt` writers and readers.
**Fix:** record a per-role load time and honour it per role.

### BUG-15 — `withTimeout` can leave its promise unsettled forever (LOW/MEDIUM)

`src/utils/withTimeout.ts:71-76` runs `onTimeout?.(error)` and `abortController?.abort(error)`
*before* `fail(error)`. `abort()` invokes listeners synchronously; a throwing listener (or a
throwing `onTimeout`) leaves the returned promise pending forever while the caller awaits it —
and the same applies to the `onAbort` path at `:70`.

**Verified:** read the timer and abort paths.
**Fix:** settle first, then run the callbacks defensively.

### BUG-16 — Media-path sync can stamp every placeholder row in a room (MEDIUM)

`src/agent/index.ts:720-744` updates `messages` by `(platform, chat_room_id, provider_message_id)`
without an `isUsableProviderMessageId` guard, although the dedupe index excludes
`''/unknown/null` (`src/db/schema.ts:79-83`) and WhatsApp emits `message.key.id || 'unknown'`
(`src/providers/whatsapp.ts:688`). A placeholder id therefore matches every placeholder row in
the room and stamps one message's `media_path`/`mime_type` onto all of them.

**Verified:** read the sync closure, the schema index predicate and the WhatsApp id fallback.
**Fix:** skip unusable ids.

### IG-11 — The inbox retry machinery has no consumer

`InboxService.fail()` (`src/messaging/InboxService.ts:168-194`) records a retry backoff and
`recoverStranded()` (`:207-224`) returns rows to `received`, but nothing ever selects a
`received`/`failed` row: the only `claim()` call site (`AppRuntime.ts:321`) claims the admission
already in hand. `MAX_ATTEMPTS` and the backoff are therefore inert, and a failed turn is parked
until retention deletes it. Enabling real retries changes delivery semantics (a failed agent turn
would be re-run, with its LLM cost and tool side effects), so this needs your call.

### IG-12 — Two outbox pruners with contradictory windows

`OutboxService.prune` (`src/messaging/OutboxService.ts:360-370`) deletes terminal rows after
`MEDIA_RETENTION_HOURS` (72 h default), while retention keeps them for 90 days
(`src/db/retention.ts:196-203`, armed at `AppRuntime.ts:799-803`). Which window is correct is a
data-retention decision.

### IG-13 — Two timestamp scales in one logical column

Drizzle `timestamp` columns store seconds (`src/db/schema.ts:76-78`) while inbox/outbox write
`Date.now()` milliseconds by hand (`InboxService.ts:48`, `OutboxService.ts:99`). `NORMALIZE_TS`
(`src/db/retention.ts:93`) papers over it for some readers only. Standardising is a migration.

### IG-14 — The LLM tool-call path skips per-action authorization

Restated from IG-10: `COMMAND_POLICIES` (`src/tools/registry.ts:142-148`) is enforced only on
the slash path (`registry.ts:328-333`). Every affected tool also enforces internally, so this is
defence-in-depth, not a live escalation; routing the model path through the authorized validator
changes the failure message the model sees.

### BUG-17 — The legacy identity merge corrupted two rows instead of merging them (MEDIUM)

`src/utils/IdentityService.ts:321` (the path used when canonical-identity deps are absent) took
`lidRows[0]` as the survivor regardless of which partial row was newer. The update then targeted
*every* row matching the survivor's lid **or** pn, so both rows were rewritten with the same
unique alias and SQLite raised `UNIQUE constraint failed`. The delete side additionally keyed on
`updated_at`, so it removed every row written in that millisecond — including another user's.
**Verified:** found by the new test; both symptoms reproduce on `main`.
**Fix:** the survivor is the newest candidate, and every other candidate row is deleted by its
own lid/pn.

### OI-09 (from review) — streaming preview and reload counters

The streaming preview now strips an *unterminated* think block (`stripThinkTags` only matched
closed ones, so reasoning leaked during the block and the preview could collapse to a bare
cursor) and sends nothing until real text arrives. The plugin loader uses one import generation
per load instead of one per file. The Discord forward path reads the body through a bounded
reader rather than buffering first. `handleIncomingMessage` rethrows after replying so a
transient pre-reply failure is still recorded as failed rather than acknowledged. `MemoryTool`
excludes room documents from its owner-scoped reads.

Tests added: `test/withTimeout.test.ts`, `test/textChunking.test.ts`, `test/textUtils.test.ts`
(all new), plus cases in `KnowledgeTool`, `admin`, `AppRuntime`, `agent`, `semanticMemory`,
`AuthService`, `registry.reload`, `MessagingService`, `roomKeys`, `DigestService`,
`IdentityService`. Each behavioural fix was re-run against `main` to confirm its test fails
there; the untested ones are stated below rather than claimed as covered.

Not covered by a new test (verified by reading, typecheck and the existing suites): the Discord
forward/dispatch caps, the WhatsApp socket-close bound, the PDFTool guard, and the admin body

## Optional Improvements

- **OI-01** `LoginThrottle` (`src/admin/auth.ts:227`) prunes only expired buckets; a flood from
  many distinct IPs within one window can exceed the 1000-entry soft cap. Add a hard cap that
  evicts the soonest-expiring bucket.
- **OI-02** Admin sessions are evicted FIFO (`src/admin/auth.ts:101-107`); a flood of logins can
  log the operator out. Prune expired first and evict the soonest-expiring.
- **OI-03** `HealthMonitor.pingYtDlp` (`src/utils/HealthMonitor.ts:211`) never clears its 10 s
  kill timer on a successful exit.
- **OI-04** `FlowHandler._startPeriodicSessionCleanup` (`src/core/FlowHandler.ts:178`) is the only
  interval in the codebase without `.unref()`.
- **OI-05** `DigestService.fetchRoomTranscript` (`src/utils/DigestService.ts:241`) stops at the
  500 KB cap while walking oldest-first, so it drops the *newest* messages.
- **OI-06** `src/ai/client.ts:53` exports a `withTimeout(ms)` that returns an `AbortSignal`,
  colliding with `src/utils/withTimeout.ts`'s `withTimeout(promise, ms)`, and its `setTimeout`
  fallback is never cleared.
- **OI-07** *(investigated — not a defect)* `InboxService.admit` was reported to raise when a
  redelivery collides with the second unique index. Verified against
  `drizzle/migrations/0021_database_safety.sql:68`: the index is on the **raw**
  `(platform, chat_room_id, provider_message_id)` values and `lower(trim(...))` is only its
  `WHERE` predicate, so a case-differing id does not collide and the claim was wrong. A
  characterization test for same-event admission was added instead; no code change.
- **OI-08** `roomKeyForContext` (`src/messaging/roomKeys.ts:231-240`) validates an explicit key's
  platform but not its remote room id, unlike its own comment.
