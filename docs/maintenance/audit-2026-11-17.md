## Critical Bugs

### BUG-01 — Provider chunking counts code points, but Telegram counts UTF-16 units (HIGH)

`src/utils/textChunking.ts:56-83` splits by `Array.from(text)` (code points). Telegram's Bot API
enforces its 4096 limit in **UTF-16 code units** (documented; entities are UTF-16-offset too), so a
chunk of 4096 emoji is 8192 units and the send fails with `400 message is too long`. The same file's
own preview clamp (`src/agent/index.ts:189-198`) was already moved to UTF-16 for this reason, so the
two disagree. Discord's limit is code-point based and stays as is.

**Verified:** read the chunker and every provider call site; confirmed the Telegram limit semantics
against the Bot API documentation.
**Fix:** give `chunkTextSmart` a measurement mode and chunk Telegram/replies in UTF-16 units without
splitting a surrogate pair.

### BUG-02 — `editMessage` head is split by code points as well (MEDIUM)

`src/providers/telegram.ts:678-692` slices `Array.from(nextText)` at 4096 *code points* for the head
of an edit. An emoji-heavy answer produces a head over 4096 UTF-16 units, which `editMessageText`
rejects — every streaming edit of such an answer throws and the preview is degraded to a plain reply
(losing the edit path entirely).

**Verified:** read the implementation; same root cause as BUG-01.
**Fix:** derive the head with the shared UTF-16 splitter.

### BUG-03 — Recurring monthly reminders drift to a day the user never chose (HIGH)

`src/utils/Scheduler.ts:442` anchors the monthly cadence on `reminder.created_at.getDate()`. The
first fire is `remindAt`, which is almost never on the creation day (`in 3 days`, `tomorrow 9am`, and
even `every month at 9am` set after 09:00 → tomorrow). So a reminder set 2026-11-28 for Dec 1 with
`monthly` fires Dec 1 and then **Jan 28**; a reminder set on the 30th at 20:00 for `monthly` fires the
31st and then the 30th of every later month. The row carries no memory of the intended anchor day,
and the previous fallback (`remindAt.getDate()`) is the *clamped* date of the last fire.

**Verified:** read `nextMonthly`, the fire loop, `ReminderTool`'s insert and the schema — no anchor
column exists in any migration.
**Fix:** persist the anchor day at scheduling time (`reminders.anchor_day`, migration `0025`), use it
at fire time, and fall back to the old values for pre-migration rows.

### BUG-04 — A sub-threshold summarization batch silently drops messages from the model context (MEDIUM)

`src/utils/ConversationSummarizer.ts:126-143`: `activeEntries` is computed *before* the min-batch
decision. When the overflow is 1…`minBatch-1` messages (the common case: 8-message batch threshold,
16-message lookahead), the batch is discarded with the comment "they stay in the active window" — but
the window was already capped, so those oldest messages are neither summarized nor sent to the model
that turn. Every summarizing room reads history with a silent 1…7 message hole.

**Verified:** read the service, the agent's call (keepCount = context limit, minBatch = 8,
lookahead = 16) and the fetch limit.
**Fix:** when the batch is below threshold, widen the active window to cover the overflow.

### BUG-05 — Knowledge retrieval ignores unembedded chunks entirely (MEDIUM)

`src/utils/roomKnowledge.ts:384-407`: when embeddings are enabled and any embedding exists, the
vector path filters rows without a matching-space embedding and then **returns** `hits.slice(...)`
— often an empty array — without reaching the keyword fallback. `embedChunkBatch` deliberately
stores chunks unembedded when a batch fails, and the type comment promises those are "retrievable by
keyword only until backfilled". They are in fact unreachable, as are all chunks embedded under a
previous model space. The documented contract ("falls back to keyword when embeddings are
unavailable") is therefore only honoured when the whole service is off.

**Verified:** read the retrieval function, `embedInCurrentSpace`, and the ingest path's `null` batch.
**Fix:** fall through to keyword scoring whenever the vector pass produced no hits.

### BUG-06 — The weekly media digest reports Monday 00:00 → Monday 08:00, not a week (MEDIUM)

`src/utils/DigestService.ts:477-478, 540-551`: the rollup window is "created at or after Monday of
*this* ISO week" with no upper bound, and the loop first fires on Monday after `DIGEST_HOUR_UTC`.
On a long-running deployment the digest therefore lists only the first hours of Monday and marks the
week done; items added Tue–Sun are never reported. What the feature reports depends on when the
process happened to restart.

**Verified:** read `weekKey`, the fire loop, the marker key and `loadWeeklyMedia`.
**Fix:** report the completed week (`[previous Monday, this Monday)`), bounding the query on both
sides and keying the cache by the window.

### BUG-07 — `/tasklist` is hijacked into an unattended agent run (MEDIUM)

`src/utils/scheduledTasks.ts:62-66` matches with `startsWith('/task')` and no delimiter. A reminder
whose text begins with `/task…` (`/taskforce call at 9`, `/tasklist …`) is executed as an LLM agent
task in an allowlisted room — spending budget and running tools — and the reminder the user wrote is
never delivered. `isAgentTaskMessage` inherits the same predicate.

**Verified:** read the parser and `Scheduler`'s use of it.
**Fix:** require a word/sentence boundary after `/task`.

### BUG-08 — A known source can be rate-limited out by its unseen sibling key (MEDIUM)

`src/webhooks/utils.ts:298-301`: the capacity guard refuses the request when *any* key is unseen and
the bucket map is full, directly contradicting the comment above it ("a known key is always
rate-limited on its own tokens"). With keys `[source:<route>:<source>, ip:<peer>]`, a long-lived
sender is rejected whenever its peer address is new (NAT rebind, proxy change, `unknown`) while the
map sits at `WEBHOOK_RATE_LIMIT_MAX_SOURCES` — the lockout the comment claims was fixed.

**Verified:** read `consume`, the pruning rule and both callers' key sets.
**Fix:** refuse only when *every* key is unseen; track unseen keys only while there is capacity, and
otherwise let the request through on the ephemeral bucket so the map cannot grow. Once the map is
full, an unknown peer key is not individually throttled — but every authenticated request still
carries its known `source:` key, which is the bucket that matters for abuse.

### BUG-09 — Exceeding the destination cap drops an entire media notification (MEDIUM)

`src/webhooks/WebhookServer.ts:333-335` throws `400` from `addTarget` once
`targets.length >= maxDestinations`. The subscription fan-out is unbounded (every admin-subscribed
room is added at `:367`), so a Jellyfin/Seerr notification in a deployment with more rooms than
`WEBHOOK_MAX_DESTINATIONS` throws before *any* target is dispatched: zero rooms are notified and the
sender gets a 400. Over-fan-out should degrade, not fail closed with nothing delivered.

**Verified:** read `handleMediaWebhook`, `addMediaTargets` and `addTarget`; the explicit
`room_ids` request path already validates its own count separately.
**Fix:** stop adding once the cap is reached, log the dropped count, and keep the explicit-request
overage as a 400.

### BUG-10 — A webhook that is still in flight is acknowledged as a completed duplicate (MEDIUM)

`src/webhooks/utils.ts:353`: `pending` means "currently being processed", but `reserve()` returns
`duplicate` for it and `WebhookServer` answers `202 {duplicate:true}`. If the first request's enqueue
then fails (503) or releases its reservation, the sender that received the "duplicate, all good" ack
never retries, and the notification is lost.

**Verified:** read `WebhookReplayCache`, `resolveReplayContext` and the handler's duplicate branch.
**Fix:** distinguish `in_flight` from `duplicate`; answer the former with a retryable 503.

### BUG-11 — A partially delivered webhook releases its replay key but answers non-retryably (MEDIUM)

`src/webhooks/WebhookServer.ts:278-281`: on partial failure the handler calls `releaseReplay()` and
returns `207` (a 2xx). Retrying senders therefore re-send to the destinations that already received
the message (the duplicate the cache exists to prevent), while GitHub — the one guaranteed retrying
sender — sees a success and never redelivers the failed ones.

**Verified:** read the sync dispatch path and the replay helpers.
**Fix:** keep the reservation once anything was delivered (`207`), and only release + answer `502`
when nothing was delivered at all.

### BUG-12 — Prometheus label values are interpolated unescaped (MEDIUM)

`src/utils/HealthMetrics.ts:363-364, 383, 390, 397-399, 406-408, 426` interpolates provider, tool,
model and service names straight into `{label="…"}`. Those names come from env/model ids and tool
registration; a `"` or backslash in one produces a malformed exposition line, and the scrape as a
whole fails — the surface an operator uses to notice an outage.

**Verified:** read `getPrometheusMetrics` and the recorders that fill those maps.
**Fix:** escape `\`, `"` and newlines in every interpolated label value.

### BUG-13 — `/metrics` ignores `X-Metrics-Token` whenever a Bearer header is present (LOW)

`src/webhooks/WebhookServer.ts:473-475` uses `bearer ?? headerToken`, while every other auth path
accepts *either* credential. A reverse proxy that injects its own `Authorization` header upstream
makes `/metrics` permanently 401 even with the documented `X-Metrics-Token`.

**Verified:** read `handleMetrics` and `authenticateSharedSecret`.
**Fix:** accept the token in either header.

### BUG-14 — `handleAction` has no error boundary (MEDIUM)

`src/admin/routes.ts:287-313`: `handleRead` catches and returns a JSON error, `handleAction` does
not. `actionDeleteKnowledge` deliberately throws for a malformed document id, and any DB failure in
the other actions escapes to the webhook server's catch, answering a bare `500 Internal server error`
instead of the `{ok:false,message}` 400 contract every other action uses. Unknown action paths are
also only rejected after the body was read, so a malformed body on an unknown path answers 400 rather
than 404.

**Verified:** read both handlers, `readJsonObjectBody`, and `actionDeleteKnowledge`.
**Fix:** resolve the action first, then read the body, and wrap the dispatch in the same try/catch.

### BUG-15 — IPv6 loopback gets a `Secure` cookie and locks the dashboard (LOW)

`src/admin/auth.ts:222` takes `host.split(':')[0]`, so `[::1]:3500` yields `"["`, `isLoopbackHost`
says no, and the session cookie is issued `Secure` over plain HTTP. The browser drops it, `verify`
401s, and the login page loops with no error. A trailing-dot `localhost.` fails the same way.

**Verified:** read `shouldUseSecureCookie` and `isLoopbackHost`.
**Fix:** parse the Host header with `URL` and pass the hostname.

### BUG-16 — `LoginThrottle`'s FIFO eviction comment is false and can reset an active bucket (LOW)

`src/admin/auth.ts:241-252`: re-arming an expired bucket with `set()` on an existing key does not
move it to the tail, so insertion order does not track recency and a currently limited bucket can be
the "oldest" one evicted — handing that IP a fresh budget.

**Verified:** read `attempt`/`prune` and the eviction branch.
**Fix:** delete before set so a re-armed bucket moves to the tail.

### BUG-17 — `setPrivilegeOverride` keeps the read-then-insert race `setRole` was fixed for (LOW)

`src/utils/AuthService.ts:487-509` selects, awaits, then inserts when absent. `role_privileges.role`
is the primary key, so two concurrent privilege commands for the same role make the second insert
fail with a PK violation — exactly the failure `setRole` documents and fixes with an upsert.

**Verified:** read both methods and the schema's primary key.
**Fix:** use `onConflictDoUpdate` on `rolePrivileges.role`.

### BUG-18 — Numeric Jellyfin webhook fields are discarded (LOW)

`src/webhooks/adapters/media.ts:42-45` reads `Year`, `SeasonNumber00` and `EpisodeNumber00` through
`asNonEmptyString`, which returns `null` for numbers. The Jellyfin plugin serialises these as JSON
numbers, so every "New Media Added" line loses its year and every episode loses its `SxxEyy`.

**Verified:** read the adapter and the helper.
**Fix:** add a scalar-to-string helper that accepts string or finite number.

### BUG-19 — A throwing flow processor leaves the session active forever (MEDIUM)

`src/core/FlowHandler.ts:477-484`: the catch logs, replies `flow.error`, and returns `true` without
clearing the session. Every subsequent message is swallowed by the same failing step until the TTL
(or `/cancel`). This is deterministic for the two PDF collection flows: they await `ctx.mediaReady`,
and once that promise rejects it never resolves.

**Verified:** read `handle`, the PDF flow processors and `mediaReady`'s rejection path.
**Fix:** clear the session on a processor failure.

### BUG-20 — The model tool-call path never applies the per-action authorization table (MEDIUM)

`src/tools/registry.ts:313-333` claims the `COMMAND_POLICIES` table now applies "for both entry
points", but `isToolInvocationAccessible` is only reachable from `validateAndAuthorizeInvocation`,
whose single caller is the slash-command path (`registry.ts:380`). `src/agent/index.ts:328` validates
model tool calls with `validateToolArguments`, which has no access context. Today `language.set`
(admin-only in the table) is the concrete gap: the tool is `user`-visible, and its own guard only
fires in groups. Future table entries would be silently unprotected.

**Verified:** traced both call paths and every `COMMAND_POLICIES` entry.
**Fix:** pass an access context into the model path's validation and reject on the access keyword.

### BUG-21 — `key=value` overrides corrupt positional binding in the command parser (MEDIUM)

`src/tools/ParameterValidator.ts:190-221`: `index` counts entries in `positional`, but the non-trailing
branch reads `values[index]`, which still contains the override tokens; and the `index >=
positional.length` `break` skips later override-only fields. `/pdf edit_metadata title=Report The
Final` sets `author = "title=Report"` and `subject = "The"`; `/notify add room_id=123` drops
`room_id`.

**Verified:** traced both examples through the loop by hand.
**Fix:** bind positionals from `positional` only, and skip (not `break`) when the cursor is exhausted.

### BUG-22 — Digest marker pruning never runs in a media-only deployment (LOW)

`src/utils/DigestService.ts:423` calls `pruneDigestMarkers` only from `runDailyDigests`, which
returns early unless `DIGEST_ROOMS` is configured. A media-only deployment (`DIGEST_MEDIA_ENABLED`
without rooms) therefore accumulates `digest:media:*` rows in `app_kv` forever; nothing else prunes
that table.

**Verified:** read both digest loops and `pruneDigestMarkers`.
**Fix:** prune in the weekly path too.

### BUG-23 — `safeDeleteSession` cannot catch a rejected `run()` (LOW)

`src/core/FlowHandler.ts:419-425` wraps a `void db.delete(...).run()` in a synchronous try/catch.
The docstring promises failures are logged; a rejected thenable escapes and becomes an unhandled
rejection (fatal under Bun). `writeSession` in the same file already hedges this correctly.

**Verified:** read the helper and the sibling's comment.
**Fix:** `.catch()` the promise.

### BUG-24 — A synchronously throwing health check escapes the interval (LOW)

`src/utils/HealthMonitor.ts:112-121`: `check()` is only caught if it returns a rejected promise. A
future check that throws before going async escapes `run()`; from `setInterval` that is an uncaught
exception, i.e. the health monitor kills the process instead of reporting `unhealthy`. Latent today
(all five checks are `async`).

**Verified:** read `schedule` and the five checkers.
**Fix:** catch synchronous throws like `WebhookServer`'s readiness check does.

### BUG-25 — The config view can print credentials embedded in URLs (LOW)

`src/admin/data.ts:442-452` redacts by variable *name*. `AI_API_BASE_URL`, `EMBEDDING_ENDPOINT`,
`JELLYFIN_URL`, `SEERR_URL` and `SEERR_API_URL` are all in the allowlist and none matches
`SECRET_PATTERN`, so a value like `https://user:key@host/v1` or `?api_key=…` is shown verbatim in the
dashboard.

**Verified:** read `configInventory` and the allowlist.
**Fix:** strip `userinfo` and secret-named query parameters from URL-shaped values.

### BUG-26 — A non-finite stored vector yields NaN similarities (LOW)

`src/utils/semanticMemory.ts:51-52` guards only `denom === 0`. A blob holding NaN/Inf (legacy or
corrupted row) makes `cosineSimilarity` return `NaN`, which fails the dedupe comparison silently
(duplicates get inserted) and makes sort comparators return `NaN` — arbitrary ordering instead of
"no match". `vectorMatchesSpace` checks only byte length.

**Verified:** read the similarity helper, `vectorMatchesSpace` and both callers.
**Fix:** treat any non-finite result as `0` and reject non-finite vectors on decode.

### BUG-27 — The Grafana adapter only matches a header Grafana does not send (LOW)

`src/webhooks/adapters/index.ts:13-14` keys on `x-grafana-origin`. A Grafana generic-webhook contact
point sends JSON only, so real alerts fall through to the generic formatter and render
`📨 Webhook payload received`. Tests fabricate the header.

**Verified:** read the dispatcher and `adaptGrafana`; nothing inspects the alert payload shape.
**Fix:** also detect by body shape (`alerts` array / `receiver` string).

### BUG-28 — The 100 MB PDF cap runs after the whole file is buffered (LOW)

`src/tools/PDFTool.ts:161-165` (and `:392-395`) reads the file and only then checks
`MAX_PDF_BYTES`. Provider media is allowed up to 200 MB, so the guard bounds what pdf-lib parses but
not what the process allocates.

**Verified:** read both paths and `HARD_MEDIA_MAX_BYTES`.
**Fix:** `stat` before `readFile`.
