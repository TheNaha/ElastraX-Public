## Critical Bugs

### BUG-01 — The streaming preview re-posts a long answer's tail on every edit (HIGH)

`src/agent/index.ts:1186-1198` builds `displayText` from the whole accumulated text and calls
`ctx.editMessage(sentKey, displayText)` every `editInterval`. Both Discord
(`src/providers/discord.ts:575-589`) and Telegram (`src/providers/telegram.ts:649-660`)
implement `editMessage` as "edit the first 2000/4096 chars, then `send()` the remainder as new
messages". With `AI_STREAMING=true`, every edit past the platform limit therefore re-sends the
whole remainder, and the final edit sends it once more: a 6000-character Discord answer is
delivered as a dozen stacked copies of its tail.

**Verified:** read the streaming loop and both provider `editMessage` implementations.
**Fix:** freeze the preview below the smallest platform limit; the final edit still delivers the
full text (head + one continuation).

### BUG-02 — Outbox idempotency conflicts ignore the direct-send grace (HIGH)

`src/messaging/OutboxService.ts:104-114` inserts with `ON CONFLICT … DO NOTHING`, so a turn
re-run for an event whose outbox row already exists in `failed`/`pending` keeps the *old*
`available_at` — which is in the past — even though `enqueueDirectText` is meant to park the row
for `DIRECT_SEND_GRACE_MS` while the caller sends the message itself. The 1 s poller claims the
stale row and delivers the previous text while the agent sends the new one: a duplicate,
user-visible message.

**Verified:** read `enqueueText`, `enqueueDirectText`, `claim` and the agent call sites; the grace
only applies when the insert actually lands.
**Fix:** on conflict, `DO UPDATE` the row's `available_at` (and payload) while it is still
`pending`/`failed`.

### BUG-03 — `recordTextDelivered` leaves a retryable row behind after a streamed reply (HIGH)

`src/messaging/OutboxService.ts:160-178` inserts `state='sent'` but does nothing when the
`(platform, idempotency_key)` row already exists in `failed`. The agent calls this after a
successful streamed delivery (`src/agent/index.ts:1377`), so the leftover `failed` row is still
claimable and the same text is delivered a second time.

**Verified:** read the insert, `claim`'s `state IN ('pending','failed')` predicate and the caller.
**Fix:** promote an existing non-`sent` row to `sent` instead of ignoring it.

### BUG-04 — Every message without a provider id shares one outbox idempotency key (MEDIUM)

`src/agent/index.ts:1377,1383` key the outbox row on `[ctx.messageId, 'assistant']`, but WhatsApp
reports `message.key.id || 'unknown'` (`src/providers/whatsapp.ts:699`). Every such message in a
room hashes to the same key, so the second reply's insert is suppressed: if that reply's direct
send fails there is no row to retry and the message is lost. `InboxService.eventKeyFor`
(`src/messaging/InboxService.ts:35`) already randomises for this case; the outbox does not.

**Verified:** read both call sites, the WhatsApp id fallback and `eventKeyFor`.
**Fix:** make an unusable message id non-deduplicable in the outbox key as well.

### BUG-05 — A quoted media note drops the current message's inlined image (MEDIUM)

`src/agent/index.ts:987-989`: when the current message embeds an image `finalContent` is an
array of content parts; the "quoted attachment omitted" branch replaces it with the plain text
string, so the model never receives the user's attachment whenever they reply to a media
message with an image.

**Verified:** read `buildMediaParts` and the branch.
**Fix:** append a text part when the content is an array.

### BUG-06 — A usage-only SSE chunk aborts an otherwise successful stream (MEDIUM)

`src/ai/client.ts:390-392` throws `AIProtocolError('invalid_chunk')` for any chunk without a
`choices` array. OpenAI-compatible gateways commonly terminate a stream with
`{"usage":{...}}` (no `choices`) when usage reporting is requested on the stream path. The
error arrives after text has been yielded, `ModelRouter` refuses cross-provider fallback for
protocol errors, and the agent replaces a complete answer with "internal error".

**Verified:** read `normalizeStreamChunk`, the generator's error handling and `ModelRouter`'s
fallback predicate.
**Fix:** treat a chunk with no `choices` as usage-only (`choices: []`) rather than malformed.

### BUG-07 — Telegram `editMessage` splits surrogate pairs at the limit (MEDIUM)

`src/providers/telegram.ts:649-652` does `nextText.slice(0, TELEGRAM_TEXT_LIMIT)` and
`nextText.slice(TELEGRAM_TEXT_LIMIT)`. `chunkTelegramText` iterates code points precisely to
avoid this, so an emoji straddling index 4096 leaves a lone surrogate in each half and the user
sees U+FFFD twice. Discord's `truncateDiscordText` already does it correctly.

**Verified:** read both implementations.
**Fix:** derive head/remainder with `Array.from`.

### BUG-08 — Boundary chunking mixes UTF-16 offsets with code-point indices (MEDIUM)

`src/utils/textChunking.ts:66-68`: `characters` is `Array.from(text)` (code points) but
`lastBreakOffset` returns a UTF-16 index into `boundary.join('')`, which is then used as a
code-point offset. Any astral character in the window shifts the split past the delimiter it
found, so a chunk ends mid-word.

**Verified:** read the helper and its caller; traced `"a😀b c"` with a small limit.
**Fix:** convert the UTF-16 offset back to a code-point count.

### BUG-09 — Discord seeds the owner role twice, racing the unique index (MEDIUM)

`src/providers/discord.ts:172-182` registers `markReady` for both `clientReady` and `ready`;
discord.js 14 emits both on first login, so `seedOwner` runs twice concurrently.
`AuthService.setRole` (`src/utils/AuthService.ts:308-337`) is read-then-insert against
`user_roles_platform_user_scope_unique_idx`, so both calls see no row and the second INSERT
fails with a UNIQUE violation, logged as "Failed to seed owner role" on every fresh deployment.

**Verified:** read the listeners, `seedOwner`, `setRole` and the unique index.
**Fix:** make `setRole` an atomic upsert and make `markReady` idempotent.

### BUG-10 — `terminate()` untracks a child that is still running (MEDIUM)

`src/providers/process.ts:177-183` sends SIGTERM and immediately `activeProcesses.delete(child)`.
The child lives on for the 2 s SIGKILL grace, so a shutdown inside that window neither kills it
nor counts it: `cancelActiveProcesses()` under-reports and the child can outlive the parent.

**Verified:** read `terminate`, `cleanup`, `cancelActiveProcesses`.
**Fix:** delete the entry in `cleanup()` (on close/settle) only.

### BUG-11 — `start()` returns a stale in-flight promise after `stop()` (MEDIUM)

`src/providers/whatsapp.ts:147-155` returns `this.startPromise` whenever it is non-null, but
`stop()` never clears it. A start issued while the previous run is still unwinding resolves with
that run, which returns early on its generation check: no socket, no reconnect, yet `start()`
reports success and WhatsApp stays offline. Discord and Telegram both gate on
`providerStatus === 'starting'` here.

**Verified:** read `start`, `stop` and the sibling providers.
**Fix:** only reuse the in-flight promise while the provider is actually starting.

### BUG-12 — A failed daily digest retries with a full LLM call every 60 s, forever (MEDIUM)

`src/utils/DigestService.ts:400-403` (and `:454-457` for the weekly rollup) releases the
exactly-once marker on failure, and `start()` (`:339`) polls every 60 s for the rest of the day.
Any persistent failure — no sender registered, provider down, Jellyfin unconfigured — therefore
re-runs `summarizeRoom` (a paid model call) up to ~960 times per room per day. The scheduler's
reminder path already has an attempt cap and backoff for exactly this reason.

**Verified:** read `claimMarker`/`releaseMarker`, both digest loops and the poll interval.
**Fix:** per-room attempt counter with a hard cap for the day's digest.

### BUG-13 — The schema contract only guards 47 of the 52 indexes (MEDIUM)

`src/db/migrations.ts:102-150`: comparing a freshly migrated database (52 indexes) with
`REQUIRED_INDEXES` (47) shows `reminders_claimed_at_idx`, `user_roles_role_idx`,
`memories_category_idx`, `message_inbox_room_idx` and `canonical_identities_platform_updated_idx`
are unguarded — exactly the indexes the Phase-2 audit added. Dropping one (bad snapshot, manual
`DROP INDEX`) passes `validateSchemaContract` and boot proceeds on unindexed hot paths.

**Verified:** migrated a fresh `:memory:` database with `drizzle-orm/bun-sqlite/migrator` and
diffed `sqlite_master` against the list.
**Fix:** require all five.

### BUG-14 — Oversized-response errors report fabricated request metadata (LOW/MEDIUM)

`src/utils/BaseHttpClient.ts:224` throws `new HttpClientError('HTTP', response.status ? 'GET' : 'GET', '', …)`,
shadowing the real `service`/`method`/`path` parameters: every size failure is attributed to
service `HTTP`, method `GET`, path ``, which defeats the per-service error attribution the class
exists for (and `method` is a ternary with identical branches).

**Verified:** read `readJsonResponse` and the three sibling throw sites.
**Fix:** pass the real values.

### BUG-15 — Rate limiting runs before the trigger decision (MEDIUM)

`src/agent/index.ts:556-571` consumes the sender's budget and replies "rate limited" for *every*
inbound message, including group chatter the bot was never addressed in (`shouldTriggerAI` is
computed at `:578`) and an in-progress flow step (`FlowHandler.handle` at `:600`), which is
dropped while the session stays active.

**Verified:** read the ordering of the rate-limit block, the trigger computation and the flow
handler call.
**Fix:** handle flows first, rate-limit only messages the bot will actually process, and keep
slash commands limited.

### BUG-16 — Backup pruning trusts the manifest path and never sweeps orphans (MEDIUM)

`src/db/backup.ts:206-232`: `join(backupDir, manifest.snapshot.file)` with no `basename` check,
so a planted manifest can make `pruneBackups` unlink a file outside the backup directory.
Conversely the snapshot is published before its manifest (`:276-279`), so a crash in between
leaves a `.db` that no code path ever deletes — unbounded growth in the backup directory.

**Verified:** read `parseManifest`, `pruneBackups`, `publishAtomically` and `backupDatabase`.
**Fix:** reject a `file` that is not a bare filename; sweep snapshots with no manifest.

### BUG-17 — `withImmediateTransaction` strands an async callback's promise (LOW/MEDIUM)

`src/db/runtime.ts:128-136` rolls back and throws when the callback returns a Promise, but the
promise keeps running unobserved: its continuation writes in autocommit after the rollback and a
later rejection surfaces as an unhandled rejection (fatal under Bun's default policy).

**Verified:** read the helper and its callers (all synchronous).
**Fix:** observe and swallow the abandoned promise before throwing.

### BUG-18 — A deleted original makes Telegram lose the whole answer (MEDIUM)

`src/providers/telegram.ts:576-580` always sets `reply_parameters` for the first chunk. If the
user deletes their message in the seconds before the reply, the Bot API returns 400 and the send
fails — with no fallback, so the answer is lost.

**Verified:** read the send loop.
**Fix:** retry chunk 0 without `reply_parameters` on that specific failure.

### BUG-19 — Every documented `convert_media` option fails validation (MEDIUM)

`src/tools/MediaConvertTool.ts:87-121` builds `-crf <0-63>`, `-b:a <bitrate>`, `-preset <name>`
and `scale=-2:<height>` from its `quality`, `preset` and `resolution` parameters, but
`FFmpegConverter.validateArguments` (`src/utils/FFmpegConverter.ts:119-134`) allows none of them:
`-crf` and `-b:a` are not on the flag list, preset names and bitrates are not allowed values, and
`scale=-2:720` fails the `^scale=\d+:\d+$` pattern. Every one of those parameters therefore threw
"Unsafe or unsupported FFmpeg value" and surfaced as a generic `convert.error`. Nothing exercised
them: no test mentions crf, preset or a `NNNp` resolution.

**Verified:** read the `-quality`/`-preset` branch and the converter's allowlist; traced
`quality=23`, `quality=128k`, `preset=medium` and `resolution=720p` through `validateArguments`.
**Fix:** allow the flags and value shapes the tool actually builds (`-crf`, `-b:a`, the encoder
presets, `scale=-2:<height>`, a chained `-vf`), keeping every other value rejected.

### BUG-20 — A plugin tool named after an existing alias captures that command (MEDIUM)

`src/tools/registry.ts:631-638`: the admission check looked for collisions only among the
candidate's *aliases* (`nextAliasMap.has(alias)`), then wrote the candidate's *name* into the
alias map. A plugin tool named `broadcast` was therefore admitted and overwrote `OwnerTool`'s
alias, so `/broadcast` dispatched to the plugin for every user while `OwnerTool` kept
advertising the alias in `/menu`.

**Verified:** read `applyCandidates`, both maps' contents and every core tool's name/alias pair.
**Fix:** one `registrationConflict()` check against both key spaces.

## Performance

### PF-01 — Room-key resolution probes the schema catalog on every inbound message

`resolveOrCreateRoomKeySync` (`src/db/rooms.ts:247-305`) runs `tableExists` + `hasColumn`
(`sqlite_master` / `pragma_table_xinfo`) per call; `getRoomKeyStats` runs ~16 of them per admin
request (prior pass P-02/P-04). The schema cannot change without a migration, and
`afterMigrationCallbacks` (`src/db/index.ts:70`) exists precisely to invalidate such caches —
but nothing registers one, so the hook is currently a detached system.
**Fix:** memoise the catalog probes per handle, invalidated by that callback.

### PF-02 — `OutboxService.claim` runs UPDATE + SELECT per candidate

`src/messaging/OutboxService.ts:207-223`: the claim `UPDATE` and the row read can be one
`UPDATE … RETURNING`, halving the statements inside the write transaction every second.

### PF-03 — Digest markers accumulate in `app_kv` forever

`claimMarker` (`src/utils/DigestService.ts:89-95`) writes one row per room per day and one per
room per week; nothing prunes `app_kv`, and `src/db/retention.ts` does not cover that table.
**Fix:** drop markers older than the digest window during the daily pass.

## Flagged — need a decision (not changed)

- **IG-11** The inbox retry machinery still has no consumer; enabling it re-runs failed turns
  (LLM cost + tool side effects). Deliberately unchanged again.
- **IG-12** Two outbox pruners with different windows (`OutboxService.prune` 72 h vs retention
  90 d). The prior description is wrong in one respect: `failed` rows are retried within
  ~80 s (`exponentialBackoff` base 5 s, `MAX_ATTEMPTS` 5), so the query only ever meets terminal
  rows in practice. The real defect is the docstring claiming `failed` rows are never claimed.
  Window choice remains a retention-policy decision.
- **IG-13** Two timestamp scales in one logical column (seconds vs milliseconds).
- **IG-14** `COMMAND_POLICIES` is enforced on both entry points now, but the tool-call path still
  relies on each tool's own internal check for defence in depth.
- **IG-15** `/metrics` and `/admin` share `METRICS_AUTH_TOKEN`, but only login is rate limited:
  the token can be guessed at full request rate against `/metrics`. Fixing it means rate limiting
  an unauthenticated surface (and a policy for `x-forwarded-for` behind the documented reverse
  proxy), so it needs your call.
- **IG-16** `DELETE /admin/api/knowledge` (and the `kb remove` action) treat a missing/empty
  `documentId` as "wipe the room's whole corpus" (`src/admin/data.ts:511`,
  `src/utils/roomKnowledge.ts:497`). Requiring an explicit `all: true` changes the admin API
  contract, so it is flagged rather than changed.
- **IG-17** `ctx.signal` never reaches the LLM request: an aborted turn keeps generating and its
  reply is parked for later delivery. Plumbing a signal through `ModelRouter`/`AIClient` changes
  the AI-layer call chain; worth a decision.
- **IG-18** `ConversationSummaryService.summarize` has no per-scope lock, so a scheduled run and
  a live message in the same room can both summarize and persist an older watermark.
- **IG-19** `message_outbox.work_idx` cannot serve `claim()`'s `OR`-of-states predicate and
  `ORDER BY available_at, created_at`; fixing it needs a migration.
- **IG-20** `findRoomKeyCollisions` (`src/db/rooms.ts`) materialises whole tables; bounding it
  changes a reporting surface.
