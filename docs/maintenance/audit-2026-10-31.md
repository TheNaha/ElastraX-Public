## Critical Bugs

### CB-1 — Retention deletes all timestamp-mode rows in apply mode
- **Severity:** Critical (data-loss risk)
- **Location:** `src/db/retention.ts` (all cutoff comparisons)
- **Evidence:** `messages.created_at`, `reminders.created_at`, `flow_sessions.updated_at` are Drizzle `mode: 'timestamp'` (seconds), while `message_inbox`/`message_outbox` columns are plain integers (ms). Retention compared every column against a millisecond cutoff, so in apply mode (`RETENTION_DRY_RUN=false`) every message/reminder/flow-session row was older than the cutoff and deleted. Default dry-run masked it; `test/retention.test.ts` inserted ms into seconds columns, hiding the mismatch.
- **Fix applied:** normalize each stored timestamp to milliseconds via a `CASE WHEN col > 1e11 THEN col ELSE col*1000 END` expression before comparison, so mixed units compare correctly. No schema change; handles both ms and seconds data.
- **Verification:** `bun test test/retention.test.ts` passes (13 tests).

### CB-2 — FlowHandler no-processor path returns `false`, causing double processing
- **Severity:** High
- **Location:** `src/core/FlowHandler.ts:385-391`
- **Evidence:** When an active flow had no registered processor, the session was cleared and a reply sent, but `handle()` returned `false`. `handleIncomingMessage` treats `false` as "not in flow" and continues into slash/AI handling, so the same message was processed twice.
- **Fix applied:** return `true`. Updated `test/FlowHandler.test.ts` expectation accordingly.
- **Verification:** typecheck/lint/tests pass.

### CB-3 — Final delivery timeout could not cancel the provider send
- **Severity:** Medium
- **Location:** `src/agent/index.ts:1295-1301`
- **Evidence:** `withCancellableTimeout` was called without passing `ctx.signal` as the parent, and the reply used `ctx.signal` directly instead of the timeout's controller signal, so `DIRECT_SEND_TIMEOUT_MS` was ineffective whenever `ctx.signal` existed.
- **Fix applied:** pass `{ signal }` (timeout signal) to `ctx.reply` and `ctx.signal` as the parent abort signal, matching the other call sites.
- **Verification:** tests pass.

### CB-4 — WhatsApp `messages.upsert` did not guard `createContext`
- **Severity:** Medium
- **Location:** `src/providers/whatsapp.ts:362-390`
- **Evidence:** `createContext` was awaited inside `Promise.all(...map(...))` without a try/catch, unlike `messaging-history.set`. A throw (e.g. `ProviderLifecycleError`) rejected the whole handler and could surface as an unhandled rejection. History-sync path already wrapped it.
- **Fix applied:** wrap `createContext` in `.catch`, logging and returning `null`.
- **Verification:** tests pass.

### CB-5 — Telegram `stop()` during boot left `start()` pending 30s
- **Severity:** Medium
- **Location:** `src/providers/telegram.ts:194-286`
- **Evidence:** `settleGuard`/`ready` were locals; `stop()` incremented the generation (making `isCurrent` false) but never cleared the guard or rejected `ready`, so `onStart` returned without resolving and `start()` hung until the 30s timeout. Also `requireBot` gated on `desiredRunning` not operational status.
- **Fix applied:** store `bootSettleGuard`/`bootReject` on the instance and clear/reject them in `stop()`. Also added an early `isOperational` return to `WhatsAppProvider.start()` for lifecycle parity.
- **Verification:** tests pass.

## Integration Gaps

### IG-1 — Inbox/outbox room-scoped reads dropped null-keyed (pre-backfill) rows
- **Severity:** Medium
- **Location:** `src/messaging/InboxService.ts:91-110` (`findByRoom`), `src/messaging/OutboxService.ts:248-266` (`pendingForRoom`)
- **Evidence:** WHERE filtered only `room_key IN (...)`, despite comments claiming raw-id fallback. Rows with `room_key IS NULL` (unbackfilled) and a matching `chat_room_id` were excluded.
- **Fix applied:** OR in `(room_key IS NULL AND chat_room_id IN (...))`.
- **Verification:** tests pass.

### IG-2 — `resolveOrCreateRoomKeySync` `created` flag was unreliable under races
- **Severity:** Low
- **Location:** `src/db/rooms.ts:277-291`
- **Evidence:** `created` was set to `true` whenever the post-`INSERT OR IGNORE` re-select returned a row, even when the insert lost the race.
- **Fix applied:** set `created` from `result.changes === 1`.
- **Verification:** tests pass.

### IG-3 — Config default mismatch for `CONTEXT_MESSAGE_LIMIT`
- **Severity:** Low
- **Location:** `src/config/runtime.ts:155` vs `src/utils/ConfigService.ts:27`
- **Evidence:** runtime defaulted to 20, ConfigService to 10; the runtime field (`maxContextMessages`) is unused, but the disagreement caused confusion. Docs flagged for maintainer decision.
- **Fix applied:** aligned runtime default to 10.
- **Verification:** tests pass.
