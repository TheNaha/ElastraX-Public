# Localisation (i18n)

ElastraX replies in one of two locales, English (`en`, the default) and
Indonesian (`id`). The locale belongs to a **room**, not to the process: every
durable room row carries `chat_rooms.language`, and every user-facing string
that the bot renders itself is resolved for that room at render time.

`src/utils/i18n.ts` is the only translation table. It exports:

- `t(lang, key, vars?)` — resolve a dotted key for a locale, interpolating
  `{placeholder}` variables.
- `hasTranslation(lang, key)` — whether a key exists in the locale or the
  English fallback. Optional text (tool help metadata) uses it to fall back to a
  source string instead of rendering a raw key.
- `translations` — the `en`/`id` tables, exported so tests can enforce parity.

## Resolution and fallback

`t()` normalises anything other than `id` to `en`, so `undefined`, an unknown
locale code and a locale read from a legacy row all produce English. A key
missing from the requested locale falls back to `en`; a key missing from both
logs `[i18n] Missing translation key` and returns the key itself, so a UI still
renders legibly. Interpolation uses a function replacer, so an interpolated
value containing `$&` is inserted literally instead of re-expanding the
placeholder.

## Room language

- The room row is created with `language: 'en'` if none exists
  (`chat_rooms.language` defaults to `'en'`).
- `LanguageTool` (`/language`, aliases `/lang`, `/setlanguage`, `/setlang`) sets
  it to `en` or `id`. In a group the caller must be an admin; in a DM any
  participant may change it.
- The agent fetches the room before invoking any tool and assigns
  `ctx.language`. Slash commands, LLM turns, tool output, progress, help and
  error strings then read `ctx.language`.
- The model itself is not given the locale code. The system prompt substitutes
  `{{LANGUAGE}}` with the full name (`English`, or
  `Indonesian (Bahasa Indonesia)`), and the prompt is responsible for replying
  in that language.

## Code that renders outside a `MessageContext`

Reminders and webhook fan-out have no message behind them. They read the
language from `chat_rooms` through `getRoomLanguage(roomKey)`
(`src/db/roomLanguage.ts`), which resolves a canonical
`room:<platform>:<id>` key and, for rows that predate the canonical-key
migration, the stored raw remote id. It returns `null` when the room is unknown
or the read fails (the failure is logged), so each caller decides its default.
Digests read the same row through their own `roomConfig` query.

| Path | Language source | Default |
|---|---|---|
| Reminder fire (`src/utils/Scheduler.ts`) | `reminders.language`, captured when the reminder is created; else `getRoomLanguage(roomKey)` | `en` |
| Webhook delivery (`src/webhooks/rooms.ts`, `src/runtime/AppRuntime.ts`) | `getRoomLanguage` per destination room | `en` |
| Digest (`src/utils/DigestService.ts`) | the room row | `en` |

A reminder stores the language when it is created, so a room that switches
language later does not change the language of an already-scheduled reminder. A
webhook is different: one payload fans out to several rooms, so `WebhookServer`
renders the notice once per supported locale into
`WebhookDeliveryJob.textVariants`, and each destination receives
`pickWebhookText(job, destination.language)` (`src/webhooks/utils.ts`). `job.text`
remains the English rendering; the durable idempotency key uses the event id when
the sender supplied one, otherwise a fallback that includes `job.text`. A
caller-supplied generic `text` body is assumed to be already localised and is
sent unchanged to every room; only the server's own labels are translated.

## Tool help and slash-command errors

- `/menu` and `/help` read `help.category.<category>`, `help.tool.<name>` and
  `help.param.<name>.<param>` from the table, so help text is part of the
  localised surface.
- The live `[i/N]` tool status is rendered by `formatToolAction(...)` and
  `BaseTool.describeAction(args, lang)` using the room language.
- Argument validation is localised too. `validateAndAuthorizeInvocation(tool,
  args, context, lang)` and `parseExplicitCommand(...)` raise
  `CommandUsageError` (`src/tools/registry.ts`) carrying the translated usage
  text; the agent answers it as a usage error instead of collapsing a typo into
  `agent.internal_error`. The old English-text matching remains only as a
  fallback for errors thrown by plugins or older tool paths.

## Invariants enforced by tests

`test/i18n.test.ts` fails the build when any of these break:

1. `en` and `id` have identical key sets.
2. Every key has the same set of `{placeholder}` names in both locales.
3. Every key except the dynamic `help.tool.*`, `help.param.*` and
   `help.category.*` families is referenced literally somewhere under `src/`.
   A key nothing reads is dead weight; delete it instead of translating it.
4. Every tool that declares `readonly name` and `readonly description` has
   `help.tool.<name>` in both locales, and one `help.param.<name>.<param>` for
   every property declared directly in its `properties` block. This is the
   check `/help` depends on.

## Adding a translation key

1. Add the key to the `en` block of `translations` in `src/utils/i18n.ts`.
2. Add the same key and the same placeholders to the `id` block.
3. Call `t(lang, 'your.key', { … })` from the rendering code; pass the room
   language, never a hard-coded `'en'`, when a room is in scope.
4. Run `bun test --no-env-file test/i18n.test.ts`.

## Adding a locale

1. Add the code to the `Locale` union and duplicate the `en` block under the new
   key in `translations`.
2. Translate every value (the parity tests then keep it honest).
3. Update the locales list in `test/i18n.test.ts`, which enumerates `en`/`id`
   explicitly for the help-metadata check, and the `WebhookLocale` union in
   `src/webhooks/types.ts` if webhooks should be rendered in the new locale.
4. Extend the locale checks that hard-code `en`/`id` (for example `localeFor` in
   `src/utils/DigestService.ts` and the `WebhookLocale` handling in
   `src/webhooks/rooms.ts`) only where the new locale must be accepted; unknown
   locale codes deliberately resolve to English.
